# 科研文献 PDF 智能阅读器

帮助科研人员降低英文文献阅读认知负荷的 Web 应用：上传 PDF → 自动提取文本与图片 → 切成可渐进展开的阅读卡片 → 一键中英切换 → 自动抽取文献元数据（标题 / DOI / 作者 / 通讯作者 / 单位 / 补充材料链接），且**所有元数据字段都允许人工修正**。

## 技术栈

| 层 | 选型 |
| --- | --- |
| 前后端 | Python + Streamlit |
| PDF 解析 | PyMuPDF (fitz)，复杂排版用 GROBID 兜底 |
| 翻译 | DeepL 优先，OpenAI / Google 备选（可配置） |
| 元数据 | GROBID（本地 Docker）+ 正则回退 |
| 依赖管理 | requirements.txt |
| 密钥管理 | .env + python-dotenv |

## 项目结构

```
segemented-pdf-reader/
├── app.py                 # 主程序（Streamlit 界面层）
├── pdf_parser.py          # PDF 解析逻辑（不依赖 Streamlit，可单独测试）
├── formula_finder.py      # 公式锚点表 / 三级判据 / 区域聚类（也不依赖 Streamlit）
├── translator.py          # 翻译逻辑（DeepL / OpenAI / Google，带超时与重试）
├── image_extractor.py     # 图片提取（缩略图、按需渲染大图、与卡片关联）
├── metadata.py            # 文献元数据（标题 / DOI / 摘要）
├── requirements.txt       # 依赖清单
├── .env.example           # 环境变量模板（复制成 .env 后填 Key）
├── .gitignore             # 排除 .env / .venv / __pycache__ / *.pdf 等
├── README.md              # 本文件
└── utils/                 # （阶段 5 代码重构时创建）
    ├── pdf_parser.py      # 由根目录的 pdf_parser.py 搬入
    ├── translator.py      # 翻译接口封装
    └── metadata.py        # 元数据提取与回退策略
```

**为什么解析逻辑单独一个文件**：它不依赖 Streamlit，可以脱离网页直接跑、直接调试；
调算法时不用碰界面代码。阶段 5 会把它搬进 `utils/`。

**公式判定为什么再拆一个模块**：判据（锚点表 + 三级分类）和聚类算法加起来逻辑量很大，
混在解析器里会让 `pdf_parser.py` 难以维护；拆出来之后可以单独跑、单独验证。
它不反向依赖 `pdf_parser`，只按鸭子类型读原子块的属性。

## 常见问题（FAQ）

### 1. PowerShell 报「因为在此系统上禁止运行脚本」，无法加载 `Activate.ps1`

**原因**：Windows 默认执行策略是 `Restricted`（禁止运行任何 `.ps1` 脚本），与本项目无关，也不是装错了东西。
用 `Get-ExecutionPolicy` 可确认；本项目机器的所有作用域都是 `Undefined`，即默认的 `Restricted`。

四种解法任选其一：

| 方案 | 命令 | 说明 |
| --- | --- | --- |
| **A. 不激活（推荐）** | `.\.venv\Scripts\python.exe -m streamlit run app.py` | 一个系统设置都不改 |
| B. 临时放行 | `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` 后再 `.\.venv\Scripts\Activate.ps1` | 只对当前这个终端窗口生效，关掉即恢复原样 |
| C. 永久放行当前用户 | `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned` | 微软推荐的开发者设置；本地脚本可直接运行，从网上下载的脚本仍需数字签名；**不需要管理员权限** |
| D. 改用 cmd | 输入 `cmd` 回车 → `.venv\Scripts\activate.bat` | cmd 没有执行策略限制 |

### 2. 8501 端口被占用

换一个端口启动：

```powershell
.\.venv\Scripts\python.exe -m streamlit run app.py --server.port 8502
```

### 3. 项目统一约定

本项目所有命令统一写成 `.\.venv\Scripts\python.exe -m <模块>` 的形式，**不依赖虚拟环境激活**，从根上避开执行策略问题。

## 阶段 1 说明：卡片是怎么切出来的

解析流程（`pdf_parser.py` 负责，公式部分在 `formula_finder.py`）：

1. **取文本块（原子块）** —— 逐页用 `page.get_text("dict")` 取块，块基本对应自然段。
   同时做字符级修复：数学字母归一化、上下标转 Unicode、行尾断词拼接。
   **原子块一经生成就不再改写**（见下节「两层数据模型」）。
2. **拆出块首标题** —— 有些排版把小标题和它下面的正文归进同一个块，会把标题行单独拆出来。
3. **拆出独立成行的公式** —— 居中 + 数学字体 + 符号密度都满足的行单独成块，
   否则它会被当成正文粘进段落，后面所有基于块的公式判定都看不到它。
4. **判断单栏 / 双栏** —— 把每个文本块的横向范围投影到 x 轴上、按字符数累加覆盖量，
   双栏排版会在页面中部出现一条覆盖量明显偏低的竖直带，那就是中缝。
   （早期版本靠「左右各 ≥3 个块」判断，遇到某页左栏只有 2 个长块会漏判成单栏，
   于是左右栏文字被按 y 坐标混排，摘要和正文串成了读不通的句子 —— 已改为按文字量判断）
5. **重排阅读顺序** —— 双栏时以「通栏块」（大标题、摘要、跨栏图注）为分段点：
   通栏块之下先读完左栏，再读右栏。
6. **段落分组** —— 把被 PDF 拆成多块的同一段在**派生层**拼回去（原子块本身不动）；
   保守策略，宁可少合并也不错合并。
7. **切卡片** —— 超过上限的超长段落在句子边界切开（连字符断词会自动拼回）。
8. **识别标题** —— 综合字号（≥1.45 倍 → 一级）、加粗、章节名、编号四种证据。

**侧边栏开关**：段落自动合并、行尾连字符合并、单张卡片目标词数、默认展开卡片数。
改动任意一项都会自动重新解析（结果按「文件 + 设置」缓存，重复点击不会重算）。

**自查方法**：展开页面底部的「🔍 解析诊断」，对照 ① 每页排版检测、② 段落明细
（已按程序认定的阅读顺序编号）、⑦ 公式区域明细（列出每个区域合了哪几块）
和原 PDF，看顺序是不是「先把左栏读完，再读右栏」、公式有没有合错。

### 两层数据模型（原子块 + 段落视图）

这是本项目最容易被后续改动踩坏的地方，单独说明：

| 层 | 是什么 | 谁在读它 | 能不能改 |
| --- | --- | --- | --- |
| **原子块**（`Block`） | 从 PDF 提取出来的最小文本块 | 元数据、诊断、公式判定与聚类、图片关联 | **不可以**：任何阶段都不得改写它的 `text` |
| **段落视图**（`Paragraph`） | 由若干原子块派生出的自然段 | 内容角色分类、卡片构建、背景信息面板、界面 | 可以：它只是视图，写它不影响原子块 |

为什么要这么分：早期版本用一个 `merge_paragraphs()` **直接把后一块的文本塞进前一块**，
一旦公式碎片被并进散文，后面所有基于块的公式判定就再也看不到它了——
用户报的那个「第 9 页求和公式有一半留在句子里」正是这么产生的。
现在段落拼接是**纯派生**（`build_paragraph_groups` 返回分组索引 `[[0], [1,2], [3]]`），
公式判定前后各算一次：第一次供角色分类读整段文本，第二次把公式块单独摘出来。

### 已知限制（阶段 1）

| 现象 | 说明 | 计划 |
| --- | --- | --- |
| 图内文字标签偶尔被当成小标题 | 例如散点图里的 "Cursor C"。矢量图内的文字目前无法与正文区分 | 阶段 3 提取图片区域后一并处理 |
| 与正文同行的「行内小标题」不会单独成卡片 | 例如 "3.1.1 Task 1: Random Saccades. This task explored…" 标题与正文在同一行 | 暂不处理，保持行内阅读更自然 |
| 跨页的同一段落会分成两张卡片 | 分页处本身就存在语义断点 | 阶段 5 可考虑合并 |
| 整页大图的页面会显示「单栏」 | 页面上只有一侧有文字（另一侧是图），但阅读顺序不受影响 | 诊断标签措辞优化 |
| 扫描版 PDF 提不出文字 | 没有文字层，需要 OCR | 不在本项目范围内，会给出明确提示 |

## 阶段 2 说明：中英一键切换

### 怎么用

1. 把 `.env.example` 复制成 `.env`，在 `DEEPL_API_KEY=` 后面填上你的 Key
2. 启动应用，展开任意一张卡片，点里面的 **中文** 按钮 → 显示译文；点 **EN** → 回到原文
3. 侧边栏「🌐 翻译设置」里可以：切换后端、切换目标语言、**测试连接**、**清空翻译缓存**，
   并实时显示「API 请求 / 缓存命中 / 累计字符」计数
4. 改完 `.env` 不用重启服务，点侧边栏的「重读 .env」即可

### 实现要点

- **按需翻译**：只有你点了「中文」的卡片才会发请求，没点的不会消耗额度
- **缓存键 =（后端 + 目标语言 + 原文）**：同一张卡片来回切换只会请求一次；
  换后端或换目标语言才会重新翻译。缓存存在 `st.session_state`，关掉浏览器标签页即失效
- **失败不阻塞**：翻译出错时显示错误原因，同时继续显示英文原文，页面不会白屏
- **超时与重试**：单次请求超时 20 秒；超时 / 断网 / 429 限流 / 5xx 故障会自动重试 3 次
  （间隔 0.6s、1.2s），401/403（Key 不对）和 456（额度用尽）不重试，直接给出明确提示

### 额度

DeepL API Free 每月 **1,000,000 字符**。一篇 10 页双栏论文全文约 5 万字符，
所以满额约能翻 15~20 篇。侧边栏的计数可以随时核对有没有重复请求。

### 翻译报错对照表

| 提示 | 原因 | 怎么办 |
| --- | --- | --- |
| API Key 被拒绝（HTTP 403） | Key 填错 / 已停用 | 核对 `.env` 里的 `DEEPL_API_KEY`，注意免费版结尾要有 `:fx` |
| DeepL 本月免费额度已用完（HTTP 456） | 额度耗尽 | 等下月重置，或在 `.env` 里换 `TRANSLATOR_BACKEND=openai` |
| 连不上翻译服务 | 断网 / 代理 / 防火墙 | 检查网络，确认 `api-free.deepl.com` 能访问 |
| 翻译服务 20 秒内没有响应 | 网络慢或服务拥堵 | 直接重试 |
| 没有检测到任何翻译 API Key | `.env` 不存在或变量名为空 | 复制 `.env.example` 为 `.env` 并填 Key，再点「重读 .env」 |

## 阶段 3 说明：图片提取与侧边栏展示

### 怎么用

1. 上传 PDF 后，侧边栏底部出现「🖼️ 文献图片（N 张）」，缩略图**按页码分组**放在折叠面板里
2. 点缩略图下方的 **🔍 放大** → 主区域顶部出现「🖼️ 图片详情」，显示完整大图和元信息
   （原始像素、页面上显示尺寸、位置坐标、关联到哪张卡片），点「关闭大图」收起
3. 卡片标题上的 **🖼️×N** 标记表示：这张卡片附近有 N 张图（通常是图注那段文字）
4. 底部「🔍 解析诊断」第 ④ 节列出每张图的关联情况，第 ⑤ 节列出被跳过的图片及原因

### 实现要点

- **图片怎么找**：`page.get_images(full=True)` 拿到图片对象，`page.get_image_rects()` 拿到它在页面上的位置
- **透明背景**：科研示意图常带透明掩码（smask），代码会把掩码叠加成 alpha 通道，
  否则透明区域会渲染成黑块。颜色空间不是 RGB（如 CMYK）的会自动转换
- **内存策略（重要取舍）**：缩略图在解析时一次性生成（每张几十 KB）；
  **大图不预生成**，只在点「放大」时渲染那一张，并且只缓存最近 2 张。
  否则一篇带 20 张高清图的论文会把几百 MB 图片全塞进内存
- **关联方式**：取「同页 + 位置距离最近」的文本卡片，距离超过 140pt 或同页无文本就算关联不可靠。
  典型命中就是图片正下方的图注

### 已知限制（阶段 3）

| 现象 | 说明 |
| --- | --- |
| 矢量图画不出来 | 用线条和文字画出来的图（流程图、伪代码框、矢量坐标图）不是位图对象，`get_images()` 看不到它们。想覆盖这类图需要按区域渲染页面，属于阶段 5 的优化项 |
| 大图会被限制到 2200px 宽 | 原始 6000×4500 的图会等比缩小后显示（不失真，只是不放大到原始像素） |
| 关联是「位置最近」而非语义关联 | 跨栏大图可能关联到不相干的段落，需要人工核对（诊断面板里能看到距离） |
| 同一张图在多页重复出现会记多条 | 按「页面 + 位置」记录，便于按页浏览 |

## 阶段 4.1 说明：标题 / DOI / 摘要提取

### 怎么用

上传 PDF 后，页面**顶部**出现「📋 文献元数据」区：标题、DOI 各一个输入框，摘要一个多行框。
三者都可以**直接点击修改**，改动立即生效；每个字段下方标明**来源**，例如
「字号分析（17.2pt，第 1 页）」「第 1 页超链接」「摘要标题定位（Abstract）」。
点「↺ 用自动提取结果覆盖」可以把手动改过的内容还原。

提取失败时字段标题会变成「**标题（未找到，请手动输入）**」，不阻断使用。

### 三个字段各自的策略

| 字段 | 策略 | 依据 |
| --- | --- | --- |
| **标题** | 第一页做字号分析：取「标题区」（页面上部 55%）里字号最大的一行，把它上下紧邻的同字号行并进来（标题常折成 2~3 行）；用黑名单排除期刊名、栏目名（Report / Highlights / Authors / Copyright…） | 三篇样本的标题正好都是第一页字号最大的文字（14.3 / 17.2 / 18.9pt） |
| **DOI** | 按可靠性依次尝试：第一页超链接 → PDF 内嵌元数据 → 前两页正文正则。**全文正则很危险**（参考文献里几十个 DOI），所以只在「同一个 DOI 出现在前两页」时才采纳——那是页眉页脚，基本可断定是本文的 DOI | 三篇的 DOI 都在第一页超链接里，且都在前两页重复出现 |
| **摘要** | 先找摘要标题（Abstract / SUMMARY），再按阅读顺序往下收集，遇到 Keywords / Introduction / RESULTS / 版权行就停；**没有摘要标题的**（例如 ACM 的裸摘要）退化为「第一页第一段长正文」，并明确标注这是推测结果 | 三篇分别是：有 Abstract 标题 / 有 SUMMARY 标题 / 完全没有标题 |

### 实测准确率（三篇不同期刊的 PDF）

| PDF | 期刊排版 | 标题 | DOI | 摘要 |
| --- | --- | --- | --- | --- |
| `双栏.pdf` | ACM CHI'25（双栏） | ✅ 正确（17.2pt，两行合并） | ✅ `10.1145/3706598.3713992` | ✅ 正确 99 词（Abstract 标题定位） |
| `单栏.pdf` | ACM Games（单栏） | ✅ 正确（14.3pt） | ✅ `10.1145/3768627` | ✅ 正确 163 词（无标题，推测并标注） |
| `1-s2.0-...-main.pdf` | Cell Press / Current Biology | ✅ 正确（18.9pt，两行合并） | ✅ `10.1016/j.cub.2015.10.019` | ✅ 正确 219 词（SUMMARY 标题定位） |

**9/9 全部正确。** 但请注意：三篇样本恰好都是规范排版，**换一篇排版古怪的期刊仍可能出错**，
所以界面上的一切都可手动修正——这正是「准确性优先于自动化」的落地方式。

### 已知限制（阶段 4.1）

| 现象 | 说明 |
| --- | --- |
| 标题可能混入副标题或栏目名 | 黑名单只覆盖常见期刊用语，遇到不认识的栏目名（如 "Brief Communication"）可能漏掉 |
| 无标题摘要只能「推测」 | 程序取第一页第一段长正文，如果那一段是图注或致谢就会错，界面会明确警告 |
| 摘要可能多收 | 遇到不认识的结束标志（例如某些期刊用 "Highlights" 之外的词）会多收后面段落，界面会提示 |

## 阶段 4.2 说明：作者 / 第一作者 / 通讯作者 / 单位 / 附件链接

### 怎么用

上传 PDF 后，在「📋 文献元数据」里会多出这几组字段（全部可编辑、改动立即生效）：

- **第一作者 / 通讯作者 / 通讯邮箱**：三个单行输入框
- **作者列表**：多行文本框，**每行一位作者**
- **作者单位**：多行文本框，每行一个单位（保留原文的 ¹ ² ³ 编号）
- **附件链接**：多行文本框，每行一个 URL；下面会把每条链接渲染成**可点击的链接**，
  并注明它来自第几页、依据是什么
- 「📧 作者邮箱」折叠区：ACM 这类逐作者列邮箱的排版，会给出「姓名 <邮箱>」配对

每个字段下方都写着**来源**（例如「通讯标注段落（第 1 页）」「通讯邮箱反查（antti.oulasvirta@aalto.fi）」），
推测出来的值会带 ⚠️ 提示；右上角「↺ 用自动提取结果覆盖」可以把改过的内容一键还原。

### 提取策略（都是拿 6 篇不同出版社的论文摸出来的）

| 字段 | 怎么找 | 关键判据 |
| --- | --- | --- |
| **作者区** | 第 1 页标题下方、摘要标题（或第一段 ≥60 词的长正文）上方的所有块，**按纵向范围取** | 不能按阅读顺序取：ACM 的作者是三列网格，阅读顺序会把右栏作者排到左栏正文之后，按顺序切会漏人 |
| **作者列表** | 作者区里的短块拆成单个名字，**按版面坐标排序**（同一行按 x 从左到右） | 拆名前先去掉单位编号（`¹`、`^1,2`、`2,6`）；「`Yanxia Li School of Computer Science…`」这种名字与单位挤在一块的，在单位关键词处截断 |
| **单位** | ① 作者区里含 University / Institute / Department / School… 的块；② 第一页页脚**以编号开头**的小字块（Nature 把单位放在页脚） | 按编号标记（¹ ² ³ / 1 2 3）切条目；页脚那条要求「编号开头」，否则会把致谢和基金声明当成单位 |
| **通讯作者** | ① 显式通讯段落：`*CORRESPONDENCE` / `Corresponding Author:` / `Correspondence concerning… addressed to` / `Corresponding author at:`；② 由通讯邮箱反查（`antti.oulasvirta@aalto.fi` → Antti Oulasvirta） | **都没有就如实报「未找到」，绝不猜**（ACM 那篇就没有标注通讯作者） |
| **通讯邮箱** | 第一页 mailto 链接、通讯段落里的地址、`e-mail:` 标签后的地址 | ACM 那种逐作者列的邮箱**不算**通讯邮箱，只放进「作者邮箱」 |
| **附件链接** | 全页扫描 PDF 的链接注释 + 正文里印出来的 URL | 三重过滤：① 仓库域名（osf.io / github / figshare / zenodo / dryad / ICPSR…）或关键词直接命中；② 剔除出版社固定链接（许可协议、crossmark、期刊主页、本文 DOI）；③ 其余要求**上下文**里出现补充材料 / 数据可得之类的词。正文声明「有补充材料」但没有链接时，也如实记一条声明 |

### 已知限制（阶段 4.2）

| 现象 | 说明 |
| --- | --- |
| ACM 三列网格的「单位」是散块 | 名字与单位在同一行交错，程序按块去重后给出去重列表，**需要人工核对**（作者列表本身是准的） |
| 通讯作者可能「未找到」 | 有些期刊（如 ACM）压根不标注通讯作者，程序如实报告并给出各作者邮箱，不猜 |
| 附件链接的**分类**可能偏差 | 「补充材料 / 数据与代码 / 预注册」是按域名与上下文关键词判的，界面会给出页码与依据，链接本身是原文里抓的，可直接点开核对 |
| 作者名里的重音、连字符 | 按原样保留（`Renée`、`Jean-Luc`）；比对时做归一化，不影响通讯作者匹配 |
| 单位与作者的**对应关系**没做 | 本轮只给「单位列表」（保留 ¹ ² ³ 编号）+ 作者名上的编号，人工可对上；自动映射见阶段 4.3 的说明 |

## 阶段 4.3 说明：GROBID 交叉校验（把外部模型当「第二意见」）

### 怎么用

1. **启动 GROBID**（完全本地，不需要梯子、不需要登录）：

```powershell
docker run --rm --init --ulimit core=0 -p 8070:8070 grobid/grobid:0.9.1-crf
```
看到 `Started oejs.Server@…{STARTING}…@384ms` 就说明服务起来了（之后它加载模型时不再刷日志，看着像卡住是正常的）。
**验证**：另开一个窗口 `curl.exe http://localhost:8070/api/isalive` 返回 `true`。
**停止**：在那个窗口按 `Ctrl+C`（容器带 `--rm`，停掉自动清理）。

2. **上传 PDF**，在「📋 文献元数据」下方会出现 **「🔍 GROBID 交叉校验」** 面板：
   - 服务在 → 自动跑一次校验（约 1~3 秒，结果缓存在会话里），显示逐字段对比表；
   - 有差异的字段带「**一键采信**」按钮：单值字段直接采用 GROBID 的值；
     列表字段是「**只补空、不覆盖**」——GROBID 独有的条目追加进去，本地已有的保持不动；
   - 服务不在 → 面板只显示一句提示 + 上面那条启动命令，**不影响任何阅读功能**。

3. 换服务地址：设环境变量 `GROBID_URL`，默认 `http://localhost:8070`。

### 为什么这么设计

| 决策 | 理由 |
| --- | --- |
| 只当「第二意见」，**不自动合并** | 用户定下的原则是准确性优先：不做黑箱合并，只给「结论 + 一键采信」，最终由人拍板 |
| `consolidateHeader=0` | 不让 GROBID 偷偷联网查 Crossref——既避免网络依赖，也保证对比的是**它自己的抽取能力** |
| `includeRawAffiliations=1` | 单位优先取 PDF 原文字符串（`raw_affiliation`），比模型切碎的 `orgName` 更完整 |
| 比对前先归一化 | 大小写、重音、序号（¹²³）、标点、空白都不算差异，否则「Steve van Pelt / Steve Van Pelt」会被判成冲突，白白制造焦虑 |
| 列表「只补空不覆盖」 | 本地规则在某些版式上更干净（见记分卡），整段替换会把本地的好结果冲掉 |
| 面板上列出 GROBID 的出错案例 | 避免用户盲信外部模型 |

### 记分卡（9 篇、6 个出版社，本地 GROBID 0.9.1 CRF 镜像）

GROBID 一侧取自**落盘的真实 TEI 响应**，所以这份记分卡可离线复现；比对口径已归一化。

| 字段 | 两边一致 | GROBID 更多/更全 | 内容不同 | 只有一边 |
| --- | --- | --- | --- | --- |
| 标题 | **8/9** | 0 | 1（Nature：GROBID 把标题抽成了期刊名） | 0 |
| DOI | **9/9** | 0 | 0 | 0 |
| 摘要 | 3/9 | 2 | 3 | 1（Cell Press：本地 219 词、GROBID 0 词） |
| 作者列表 | **6/9** | 3（多出来的都是噪声，见下） | 0 | 0 |
| 第一作者 | 7/9 | 0 | 2（GROBID 的第一作者是题记人名 / 编者） | 0 |
| 作者单位 | 0/9 | 4 | 5 | 0 |
| 作者邮箱 | 4/9 | 0 | 5 | 0 |

**人工判定（重要：自动比对只能告诉你「哪里不一样」，判断不了「谁对」）**

| 差异 | 人工结论 |
| --- | --- |
| 作者列表：SAGE 多 `George Washington`、Frontiers 多 `Wolnei Caumo`/`Ariadne Brandt`、xlm 多 `Jane Kelly` | **GROBID 错**：分别是题记里的人名、侧栏的编者与审稿人、把 `Laura Jane Kelly` 拆成两半。**本地规则 9/9 作者都正确** |
| 标题：Nature HB | **GROBID 错**（抽成期刊名 `nature human behaviour`），本地正确 |
| 摘要：Cell Press | **GROBID 错**（该刊摘要叫 SUMMARY，它认不出、返回 0 词），本地 219 词正确 |
| 摘要：单栏 / ACM 网格 vs 双栏 / SAGE | 前者 GROBID 更全、后者本地更完整——**摘要字段两边都会失手，建议人工核对** |
| 作者单位 | **GROBID 通常更干净**（会合并被版面切碎的院系名、剥掉序号）；本地更贴原文。**这个字段差异最多，务必人工核对** |
| 作者邮箱 | 口径不同但互补：本地覆盖「作者区逐作者列邮箱」的排版（ACM 那类）+ 通讯邮箱；GROBID 覆盖 PDF 头部里的邮箱 |
| ORCID | **只有 GROBID 提供**（本地不做），界面上作为附加行显示 |

**结论**：本地规则在标题、作者列表、作者去噪上更强；GROBID 在**结构化**（每位作者的邮箱与 ORCID、单位归一化）上更强。两者互补——这正是交叉校验的价值。

### 这次交叉校验替本地规则抓出的 4 个真实缺陷（已修）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 单栏.pdf（ACM Games）作者数 **0** | 作者名与单位挤在同一块（`LLOGARI CASAS, 3FINERY LTD, …`），本地看到单位词就整块丢弃 | 切出「第一个逗号之前、单位关键词之前」的那段当候选人名 |
| 双栏.pdf（ACM CHI）作者数 **6**（实际 5） | 院系名 `Media Engineering Technology` 不含单位关键词、又被版面切成单独一块，通过了人名判据 | 新增「整串 token 都是学科词」的否决规则（判据是**全部**而非**含一个**，避免误杀 `Andrew Law`） |
| Cell Press 少 1 位作者 | 重音被排版拆开（`Ange ´lina Vernetti` 实为 Angéline），含重音的姓名整段判不出 | 把「字母 + ´ + 空格」合成组合尖音符再做 NFC；名字校验从 ASCII 扩到 Unicode 字母 |
| Cell Press 单位 **0 条** | 该刊把单位放在**第 2 页**，本地只找第 1 页 | 单位池扩到「第 2 页里以编号开头且含单位关键词的小字块」 |

修完这 4 处后，作者列表与 GROBID 一致的样本从 3/9 提升到 6/9（其余 3 篇是 GROBID 混入噪声）。

### 已知限制（阶段 4.3）

| 现象 | 说明 |
| --- | --- |
| 上传后多花 1~3 秒 | 服务在时会自动跑一次校验（结果缓存，同一文件不重复调用）；嫌慢可以改成只在点按钮时跑 |
| 首次调用更慢（约 5~10 秒） | GROBID 启动后第一次调用要加载模型 |
| **用的是 CRF 轻量镜像** | 500MB 的 `-crf`（纯 CPU）；官方另有 8GB 的 `-full`（深度学习模型，Windows 容器不支持 GPU、只能 CPU 跑且慢很多），只有在需要更准的参考文献/引用解析时才值得换 |
| 单位字段几乎总是不一致 | 两边切分格式不同，属正常；界面已标出差异，人工核对即可 |
| GROBID 也会出错 | 实测失效模式：标题抽成期刊名、把题记/编者/审稿人当作者、SUMMARY 式摘要抽不到。**不盲信任何一边** |
| 依赖 Docker | GROBID 走 Docker 分发（官方推荐）。不启动它时所有功能照常，只是少一个第二意见 |

## 阶段 3.5 说明：卡片流净化与「论文背景信息」

### 为什么做这一步

早期版本把 PDF 里所有文本块都当正文排进卡片流，于是页眉页脚、作者单位、期刊栏目名、
参考文献全混了进来。三篇样本的实测：

| 样本 | 全部文本块 | 属于非正文 | 占比 |
| --- | --- | --- | --- |
| `单栏.pdf` | 203 | 44 | 22% |
| `双栏.pdf` | 198 | 47 | 24% |
| Cell Press | 107 | 48 | 45% |

而且正文卡片里 30%~45% 不足 20 词（最短 1 词），读起来全是碎片。

### 现在的做法

**① 内容角色分类**（`classify_roles`）——每个文本块判定一个角色：

| 角色 | 判定依据 | 去向 |
| --- | --- | --- |
| 正文 | 剩下的都算 | 阅读卡片 |
| 章节标题 | 字号 / 加粗 / 编号 / 章节名 | 卡片内加粗显示 |
| 图注 | `Figure 3.` / `Table 2:` 这种「编号 + 标点」开头 | 阅读卡片（按你的要求视作正文） |
| 页眉页脚 | 跨页反复出现的短文本（去掉数字后比对） | 背景信息 |
| 作者与单位 | 第 1、2 页里「标题与摘要之间」的短块 | 背景信息 |
| 封面页信息 | 某页没有长正文时整页（Cell Press 那种导读版面） | 背景信息 |
| 版权 / 许可 / 资助 | ©、licensed under、grant agreement… | 背景信息 |
| 参考文献 | `References` 标题及其后的全部内容 | 背景信息 |
| 栏目名 / 标签 | Authors / Highlights / CCS Concepts / Report / 图内面板标签 | 背景信息 |

**② 卡片按阅读顺序聚合到 100~300 词**（`build_reading_cards`）

- 侧边栏「卡片目标词数」默认 200（攒到这么多词就收一张卡），实际落点 **100~300 词**
- **章节标题进卡片内部、加粗显示**，不再单独占一张卡——否则像 CHI 那种小节特别多的
  论文，每张卡都只有一两百词，凑不到目标长度
- 卡片不会跨「非正文」区域，所以不会把互不相干的两段粘在一起
- 章节末尾的零头能并进上一张就并；再超上限就先收卡，保证卡片不超过 300 词

**③ 卡片标签**：`#7 · §3.1 Task → 3.3 Determining Eye Dominance · 原文第 3–4 页 · 335 词`

**④ 论文背景信息面板**：4 个折叠分组 —— 作者与单位 / 期刊信息与栏目 / 参考文献 / 页眉页脚。

**⑤ 「显示全部内容」开关**（侧边栏）：打开后不再过滤，非正文也照原样列出来并标注角色，
用于核对过滤有没有误杀真正文。

### 实测效果

| 样本 | 卡片数（净化前 → 后） | 词数中位 | 落在 100~300 | 20 词以下的碎片 |
| --- | --- | --- | --- | --- |
| `单栏.pdf` | 203 → **25** | 227 | 25/25 | 59 → **0** |
| `双栏.pdf` | 198 → **26** | 242 | 25/26（最大 306） | 39 → **0** |
| Cell Press | 107 → **16** | 248 | 16/16 | 15 → **0** |

### 公式与统计量的处理

统计量是科研阅读的重点，但 PDF 里的数学排版会以三种方式坏掉：

| 问题 | 现象 | 处理方式 |
| --- | --- | --- |
| **数学字母符号** | `𝑇 𝑣 𝑥`（U+1D400 数学字母区）既难读、也翻译不了 | 用 NFKC 归一化成普通字母 `T v x`（单栏样本里修掉了 463 个字符） |
| **上标被拆成两块** | `ηp² = 0.16` 被切成：前块结尾 `…p = 0.021, hp`、后块开头 `2 = 0.16), …` | ① 靠「字号更小 + 底边高于本行其他字符」判断上标（**这些 PDF 的 flags 上标位根本没设**），转成 Unicode 上标 `²`；② 放宽段落合并规则，把跨块的上标粘回去 |
| **希腊字母被字体错映射** | `η` 提取出来是 `h`，于是 `ηp²` 成了 `hp²` | Cell Press 用「单字形子集字体」画 η，字体里字形名都被改写成 "LATIN SMALL LETTER H"，信息已彻底丢失。只能在统计量上下文按模式修：`hp² =` / `hp² <` → `ηp²`。这类修复按需追加，遇到新符号告诉我即可 |

实测现在能完整正确地带出：`F(1, 31) = 5.92, p = 0.021, ηp² = 0.16)`。

**公式的呈现方式（已实现：区域截图）**

先说结论：**PDF 里没有 LaTeX / MathML 源码可提取**。实测翻了 6 篇样本的全部内部对象（解压后逐流搜索）：

| 检查项 | 结果 |
| --- | --- |
| MathML 标签 `<math>` | 0 个对象 |
| LaTeX 命令 `\frac` `\begin{` `\sum` | 0 个对象 |
| OMML（Word 公式） | 0 个对象 |
| 结构树 `/StructTreeRoot` | 只有 2 篇 tagged PDF 有，且里面只有**图片 alt 文本**和**软连字符**，没有公式源码 |

原因很直白：Obsidian 之类能渲染二维公式，是因为源头是 Markdown 里的 LaTeX 源码；**PDF 是「印刷成品」，排版源码早就丢了**，公式只剩下一堆带坐标的字形。所以二维公式（分式、积分、矩阵）**无法用文本表达——这是信息维度问题，不是实现难度问题**。

因此采用**区域截图呈现**：把同一处公式的碎片聚成一个「区域」，整簇渲染成一张图。

**① 三级判据**（`formula_finder.py`，只用符号锚点，不用词锚点）

| 等级 | 判据 | 允许做什么 |
| --- | --- | --- |
| **强候选** strong | 打分 ≥4 且通过全部防线 | 单独成图；可作为区域聚类的**种子** |
| **弱候选** weak | 打分 2~3，或打分够但没过防线（降级，**不会**落回普通文字） | 只能被区域吸收；只有「相对所在栏有缩进 + 数学字体 + 括号配对」时才允许当种子 |
| **公式碎片** fragment | 词数 ≤6、无句末标点、非散文，且含数学锚点/上下标/数学字体/单字母变量 | **只能被区域吸收，绝不单独成图**（这是「不把半句话变成图片」的关键） |
| 普通文字 | 其余 | 留在正文里、照常可选中可翻译 |

打分规则：大运算符（`∑ ∏ ∫ ∮ √ ∂ ∇ ∞`）**+3**（近乎无噪声的强信号，仅凭它就能抬成强候选）；
比较运算符 +2；上下标 +2；其它数学运算符每出现一种 +1（最多 +2）；词数 ≤10 再 +1。
防线（只限制「单独成图」，不限制被吸收）：必须有变量名、比较运算符两边必须有操作数
（挡 `"<.001"` 这类表格碎片）、括号必须配对、必须相对所在栏有缩进
（正文段落一律从左边界起排，天然被排除）。

**② 区域聚类**：以强候选（合格的弱候选）为种子逐轮生长，满足任一条件就吸收一个公式候选块——

- 与当前区域外接矩形的间隙 ≤ max(8pt, 1.2 × 簇内中位字号)（约 12.6pt，与旧版口径相当）
- x/y 投影重叠 ≥30%，且**另一方向上确实相邻**（间隙 ≤ 同一阈值）
- 与簇在同一行上（y 重叠超过较矮者的一半，同栏）

散文永远吸不进来（只有公式候选能进）；单簇上限 15 块、面积 ≤ 页面 20%。
**算法清单走确定性规则**：从 `ALGORITHM 1: … / Input:` 这类真正的清单标题出发，
把连续的行整簇收进来（不受块数上限约束），并对行数、缩进做限制以免吞到正文段与页脚。

**③ 渲染**：`page.get_pixmap(clip=区域, dpi=200)`，按需渲染 + 会话内缓存。
公式出现在卡片里**原文对应的位置**上，视觉 100% 保真；代价是不可选中。

实测（6 篇不同期刊的样本，含单/双栏、Cell Press、Nature Human Behaviour、Frontiers、SAGE、ACM、xlm）：

| 样本 | 公式区域 | 说明 |
| --- | --- | --- |
| 单栏.pdf（ACM Games，16 页） | **32 个** | 含 4 个算法清单（每个整张图，含 Input/Output 与全部编号行） |
| 双栏.pdf（ACM CHI'25） | 1 个 | 该文只有一处显示公式 |
| Cell Press《Current Biology》 | 0 个 | 心理学论文只有内联统计量，**刻意不转图** |
| Nature Human Behaviour | 3 个 | |
| Frontiers / SAGE / ACM(2) / xlm | 0 个 | 同上，无显示公式 |

> **已修复的真实案例**（用户报的）：第 9 页那条 `v̄ᵢ = (1/N) ∑_{k=k−N+1}^{k} vᵢ(tₖ)`
> 在 PDF 里被拆成 4 个碎片（`vᵢ= 1`、`k∑k=k−N+1`、`vᵢ(tₖ)`、`N`），
> 修复前只有一块被转成图片、另外三块留成文字，上方散文里还残留 `…over Nframes is k ∑ k`。
> 现在 4 块聚成一个区域、整簇出一张图，散文尾部也不再残留公式文本。

> **备选方案（评估后未采用）**：OCR 把公式识别成 LaTeX（pix2tex / Mathpix）再交给 `st.latex` 渲染。
> 需要装 torch（2~3GB）或付费 API，而且**识别错误会"看起来很对"**——对科研阅读来说，
> 一张保真的原图比一个可能算错的公式更安全。

**中文视图下的公式（保持原图，不参与翻译）**

卡片切到「中文」时，正文与章节标题会**按段落分别翻译**，而**公式区域保持原图**不做任何翻译；
「显示全部内容」模式里公式段同样出图、同样不参与翻译，公式文本也不计入卡片词数与翻译字符数。

实现要点：DeepL 与 Google 的接口都支持**一次请求带多段文本**（`text=a&text=b`），
所以「按段落翻译」仍然只发**一次 HTTP 请求**——实测 3 段 1.9 秒 vs 逐段 5.8 秒；
缓存粒度也从「整卡」细化为「段落」，同一段被别的卡片复用时也能命中
（实测来回切换后请求数不再增长，命中数持续增加）。

**安全兜底**：批量调用失败时（例如断网），会退回「整卡翻译」的旧行为并显示错误提示，
所以不会出现「翻译直接坏掉」的新故障模式；公式段与「显示全部内容」下没有段落结构的条目
都会走各自的降级路径，不会把公式文字送进翻译接口。

### 已知限制（阶段 3.5）

| 现象 | 说明 |
| --- | --- |
| 个别卡片会略微超过 300 词上限 | 末尾零头并进上一张时最大到约 390 词，这是为了避免出现很短的尾卡 |
| **公式图不可选中、不可翻译** | 用区域截图换取 100% 视觉保真；中文视图里公式同样保持原图，正文则按段落翻译 |
| **公式判定不是 100%** | 以文字为主的段落刻意不转图片；少数独立公式（页面上没有强候选做种子的）可能仍留作文字。发现漏转或误转，把页码和例子发给我调规则 |
| 同一处公式偶尔被切成两张图 | 例如单栏第 9 页有两处相隔 15pt 的显示公式各出一张图（它们是两处不同的公式，不是切错） |
| 伪代码、公式仍在卡片里 | 它们确实是正文内容，只是排版特殊（以图片形式呈现） |
| 论文标题会出现在第一张卡片开头 | 与顶部元数据区重复，但保持了原文结构 |
| 角色分类不是 100% | 用「显示全部内容」开关 + 人工核对兜底；发现误判可以告诉我调规则；清单行号（单独的 `5`、`6`）有时会被当成页脚，不影响图片本身 |

## 协作约定

- 一次只推进一个阶段，通过验收测试并提交后再进入下一阶段。
- 元数据提取遵循「准确性优先于自动化」，任何字段都可人工编辑覆盖。
- 密钥只写在 `.env` 中，`.env` 永不提交。
