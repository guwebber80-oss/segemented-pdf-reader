# 科研文献 PDF 智能阅读器

帮助科研人员降低英文文献阅读认知负荷的 Web 应用：上传 PDF → 自动提取文本与图片 → 切成可渐进展开的阅读卡片 → 一键中英切换 → 自动抽取文献元数据（标题 / DOI / 作者 / 通讯作者 / 单位 / 补充材料链接），且**所有元数据字段都允许人工修正**。

## 技术栈

| 层 | 选型 |
| --- | --- |
| 前后端 | Python + Streamlit |
| PDF 解析 | PyMuPDF (fitz)，复杂排版用 GROBID 兜底 |
| 翻译 | DeepL 优先，OpenAI / Google 备选（可配置） |
| 元数据 | GROBID（本地 Docker）+ 正则回退 |
| 依赖管理 | requirements.txt |
| 密钥管理 | .env + python-dotenv |

**为什么核心逻辑都在 `utils/` 且不依赖 Streamlit**：可以脱离网页直接跑、直接调试；
调算法时不用碰界面代码，测试也能用普通 `python tests/xxx.py` 跑。
包内模块之间用**相对导入**（`from . import formula_finder`），
外部（`app.py`、`tests/`）用 `from utils import pdf_parser`。

**公式判定为什么单独一个模块**：判据（锚点表 + 三级分类）和聚类算法加起来逻辑量很大，
混在解析器里会让 `pdf_parser.py` 难以维护；拆出来之后可以单独跑、单独验证。
它不反向依赖 `pdf_parser`，只按鸭子类型读原子块的属性。

## 阶段 6.4 说明：译文覆盖与「翻译整篇」（修用户实测报的「重开还要重翻」）

**用户报的现象**（原话）：「我上传了一篇文献后加载了几张卡片后，我主动关闭了阅读器进程，
后重新打开，上传先前文献，发现在第一次切换页面时仍要重新翻译，断开网络后翻译失败，显示英文原文。」

**排查结论：本地缓存没有坏，坏的是预期。** 直接查 `.cache/` 里的实物：

* 记录在（`papers/d47df9041a500984.json`，含设置、十项元数据修正、阅读位置第 9 张）；
* 译文表在（`translations.json`），而且**看过的那两张卡 8 段全部命中**（逐段比对过哈希）；
* 但整篇 25 张卡、94 段里，表里**只有 8 段**——因为翻译是**读到哪翻到哪**的懒加载：
  没显示过的卡片从来没被翻译过，自然也没落盘。于是「重开 → 翻到没看过的卡 → 要联网翻一次」
  「断网 → 那张卡只能看英文」都是这个设计的必然结果。

**这一步做的事**：

1. **左栏新增「🌐 译文覆盖」**：如实显示「已能离线读中文：x / N 张卡 · 段落 y / M 段」，
   并说明「没翻到的卡片不会自动翻译」。一眼就能看出断网之前还差多少。
2. **新增「🌐 翻译整篇（补齐 N 段）」按钮**：把全文还没译文的段落一次翻完并**立刻落盘**。
   已译段落命中缓存、不会重复请求，所以多点几次绝对安全（第 2 次基本零请求）；
   中途失败会保留已完成的部分，修好网络后再点一次接着译。
   单栏.pdf 实测：94 段 / 5 次请求（按 20 段、2 万字符一批切分，远低于 DeepL 的单请求上限）。
3. **断网时的提示改写**：翻译失败不再只说「重新切到中文即可」，而是明确指出
   「这张卡片本地还没有译文 → 需要联网翻一次，或先点『翻译整篇』补齐」。
4. **落盘改为「与磁盘合并」**（顺手修的一个隐患）：译文表按文本哈希只增不减，
   所以写盘前先读回磁盘上的条目合并再写。否则**同时开着两个窗口/两个进程**时，
   后写的一方会把自己内存里的那几张卡覆盖上去，把对方存下的译文抹掉
   （实测怀疑就是用户这次丢译文的原因之一）。

**怎么验收**：`python tests/test_translate_plan.py`（24 条）+ `python tests/test_store.py`（51 条），
以及 `.dsh-scratch\smoke_app_upload.py`（24 条端到端：真跑 app.py，点「翻译整篇」→
**全新会话连翻 4 张卡，翻译请求 0 次**——即断网也能看中文）。

## 阶段 6.2 说明：明 / 暗模式切换

左栏上传框下面多了一个 **🌗 明 / 暗模式**（折叠面板里两个按钮：☀️ 浅色 / 🌙 深色）。
先说清楚 Streamlit 的客观限制（都是实测过 1.63 的源码，不是猜的）：

* **没有**运行时切换主题的公开 API——不存在 `st.set_theme()`，`st.set_page_config()` 也没有主题参数；
* 主题只有两条生效途径：`.streamlit/config.toml` 的 `[theme] base`（服务启动时读）、
  以及浏览器里 **☰ → Settings → Theme** 的手动切换（纯前端、立即生效、只存在本机浏览器）；
* 主题是**随新建会话下发**的（`app_session.py` 只在 `NewSession` 消息里带 custom_theme），
  所以改完配置**要刷新一次页面（F5）**才看得到；
* Streamlit 的静态样式表里**没有任何 CSS 变量**（颜色都是 emotion 内联样式），
  所以「注入 CSS 把整个界面改暗」在 1.63 上不可靠、还会随版本失效——本项目**不做**这种 hack。

因此这里的实现是：按钮一次做两件事——

1. `streamlit.config.set_option("theme.base", …)`：让**当前进程**按新主题下发（刷新即生效）；
2. 把 `[theme] base` 写进 `.streamlit/config.toml`：**重启服务后依然保持**。

写配置用的是**行级合并**（`ui/theme.py::_merge_toml`），只动 `[theme]` 段里的 `base` 这一个键：
别的段、注释、你自己加的配置一字不改，`[theme.sidebar]` 这类子段也不会串段
（`tests/test_theme.py` 用 24 条断言守着这件事）。

**两种切换方式怎么选**：

| 需求 | 用什么 | 生效速度 |
| --- | --- | --- |
| 立刻变暗、只在这台机器这个浏览器 | ☰ → Settings → Theme | 立即（浏览器本地记住） |
| 让服务端默认就是深色、换浏览器也一致、重启不丢 | 左栏 🌗 明 / 暗模式 | 按 F5 刷新后 |

### 怎么验收这一步

1. `python tests/test_theme.py` —— 24 条断言：配置合并只动 `[theme] base`（注释、别的段、
   `[theme.sidebar]` 子段都不受影响）、读回非法值按「未指定」处理、非法主题被拒绝且不写文件；
2. 界面上点一下 **🌙 深色** → 看到「已切到深色：按 F5 刷新页面即可看到」→ 按 F5 → 整个界面变暗；
3. `回归检查.bat` —— 10 个样本指纹不变 + 全部套件（新增本套件）。

### 已知限制（阶段 6.2）

* 应用内按钮**不能免刷新生效**（受 Streamlit 的主题下发机制限制，见上）；
* 按钮用的是 `streamlit.config.set_option`——非公开稳定 API，整段包了 try/except：
  万一将来改名，最坏情况是「要重启服务才生效」，不会把界面弄崩；
* 主题是全局的（写在项目配置文件里），不是「每篇文献各自记住」；
* 写出来的 `.streamlit/config.toml` **属于本机偏好，已在 `.gitignore` 里**（不会被提交）。

## 阶段 6.1 说明：本地持久化缓存（读完就存，下次接着读）

**为什么做**：翻译要花 API 额度、解析要等几秒。同一篇论文第二次打开时，这两样都不该重来。
阶段 5.3 之前所有成果只活在浏览器会话里——一刷新就全没了，元数据的手工修正也白改。

### 存了什么、没存什么

| 内容 | 存不存 | 说明 |
| --- | --- | --- |
| 译文 | ✅ 全局共享 | 键 = `后端 \| 目标语言 \| 原文哈希`，与「哪篇 PDF」解耦 |
| 元数据修正（十个字段） | ✅ 按论文 | 人工改正过的内容优先级最高，必须留住 |
| 解析设置（合并 / 连字符 / 目标词数 / 表格呈现 / 显示全部） | ✅ 按论文 | 恢复后解析指纹随之命中，结果与上次完全一致 |
| GROBID 结果 | ✅ 按论文 | 省掉一次 5~10 秒的外部调用 |
| 阅读位置（读到第几张） | ✅ 按论文 | 新会话直接回到上次那一张 |
| 插图、公式与表格截图 | ❌ | 体积大（一篇几十 MB），下次按需 200 DPI 重渲染（几百毫秒） |

### 论文身份：认字节，不认文件名

key = PDF 字节的 SHA-256 前 16 位。所以改名、挪目录、重新上传都能命中；
内容变了（期刊更新版本）就当成另一篇——此时还有**第二道兜底**：
按 DOI（归一化掉 `https://doi.org/` 前缀与大小写）或标题（只比字母数字，PDF 断行拆词也能对上）
从索引里找回记录，元数据修正与译文照旧接上。

### 文件布局与可靠性

```
.cache/papers/<key>.json   一篇文献一条记录（设置 / 修正 / GROBID / 阅读位置）
.cache/index.json          轻量索引（key → 文件名·标题·DOI·时间），按 DOI/标题找回用
.cache/translations.json   全局译文表
```

* **原子写**：先写同目录临时文件再 `os.replace`，中断不会留下半个 JSON；
* **容错读**：文件缺失、被写坏、编码不对——一律降级成「没有缓存」，**绝不让界面崩**，
  最多重新翻译一次（`tests/test_store.py` 里有 6 条断言专门守着这件事）；
* **按需落盘**：译文只在有新内容时才重写整张表，翻页不会反复写盘；
* **缓存目录可迁移**：环境变量 `PDF_READER_CACHE_DIR` 或 `store.set_cache_root()` 指到别的盘。

### 界面上的「💾 本地缓存」面板（左栏）

显示命中状态、文献条数、译文条数、占用大小与缓存目录路径，并给两个清理按钮：

* **清除本篇记录**：只删这篇的元数据修正与阅读位置（译文是全局的，不动）；
  清完**本次会话不再自动保存这篇**（否则脚本重跑会立刻写回来），换文件或刷新后恢复；
* **清空全部缓存**：所有记录 + 全部译文一起删（下次阅读重新解析、重新翻译）。

### 怎么验收这一步

1. `python tests/test_store.py` —— 缓存本身的 48 条断言（身份 / 原子写 / 容错 / 译文键 / 清理）；
2. `python ..\.dsh-scratch\smoke_app_upload.py` —— **端到端冒烟**：用 Streamlit AppTest 真跑
   app.py（假上传 + 假翻译函数，不需要 API Key），验证「第一次打开翻译落盘 → 第二次打开
   `cache_source == hash` 且翻译函数一次都没被调用 → 阅读位置原样回来」共 18 条；
3. `回归检查.bat` —— 10 个样本的指纹与基线逐字段比对（解析逻辑没动，必须 10/10 一致）+ 全部套件。

### 已知限制（阶段 6.1）

* 缓存里**没有图片**，所以「公式 / 表格截图」每次仍要现场渲染（这是刻意的取舍）；
* GROBID 结果虽然缓存了，但**面板只在 GROBID 服务可达时才展示对照表**——
  服务没启动时看到的是「启动命令」提示而不是上次的结果；
* 索引只记最近一次保存的标题 / DOI，若你把标题手工改得面目全非，按标题兜底会失效
  （按 DOI 兜底仍然有效）；
* 多个浏览器标签页同时读同一篇时是「后写覆盖」，不会写坏文件，但阅读位置可能互相覆盖。

## 阶段 5.3 说明：交互界面重做（三栏布局 + PPT 式卡片）

按用户拍板的方案把界面从「侧边栏 + 卡片列表」改成**三栏 + 单卡翻页**
（先在 `交互demo.html` 这个单文件原型里确认过效果，再落进正式应用）：

| 区域 | 内容 |
| --- | --- |
| **左栏**（功能控件） | 上传文献 · 语言开关（中文 / English，导入后默认中文）· 解析设置 · 翻译设置（后端 / 目标语言 / 测试连接 / 清空缓存）· 处理状态 · 章节导航（跳到某章）· 翻译计数 |
| **中栏**（阅读主体） | 标题 + 当前卡片；卡片左右两侧是 **‹ ›** 翻页按钮（与卡片垂直居中对齐，首尾循环）；进度条 + 「第 i / N 张」；卡片内容**居中**（两侧留白，近似 760px 文字列），文字内部仍左对齐 |
| **右栏**（背景信息） | 文献元数据（十字段可编辑）· GROBID 交叉校验 · 概览（页数 / 卡片 / 词数 / 耗时 / 公式表格区域数）· 文档结构 · 论文背景信息 · 解析诊断 ①~⑧ |

**图片点击放大**：卡片后面的文献插图、卡片里的公式与表格截图，图下都有「🔍 点击放大」，
点开是 Streamlit 原生弹层（`st.dialog(width="large")`）显示原尺寸——公式上下标、
表格小字号在卡片宽度里看不清的问题就此解决。

**中英切换**：左栏一个开关切换全部卡片的视图；中文视图按段落翻译（公式与表格保持原文截图，
引文列表不翻译），译文命中缓存就不再请求 API（左栏有请求 / 命中计数可核对）。
「显示全部内容」核对模式保持原文、不翻译，避免核对时误触发大量翻译请求。

**与 demo 的差异（如实说明）**：

| 项 | 说明 |
| --- | --- |
| 键盘 ←/→ 翻卡 | demo 里有；正式版 Streamlit 无法直接捕获键盘事件（需要自定义组件），暂未实现，先用卡片两侧的 ‹ › |
| 本地持久缓存 | demo 里的 localStorage 只是演示；正式版目前仍只有**会话级**缓存（关掉进程即失效），磁盘持久化方案已定、待实现（见「待办」） |
| 「圆点」进度 | 卡片多时会很长，正式版改用进度条 + 计数器 |

## 阶段 5 说明：代码结构整理（app.py 1158 → 492 行）

阶段 5 只做结构，**不改任何行为**——验收标准就是「10 篇样本的回归指纹与基线完全一致」。

| 步骤 | 做了什么 |
| --- | --- |
| 5.1 | 8 个核心模块收进 `utils/` 包（包内相对导入、外部 `from utils import …`） |
| 5.2a | 界面辅助拆出 `ui/media.py`（截图与公式/表格渲染）、`ui/cards.py`（卡片标签/翻译/渲染） |
| 5.2b | 两个大面板拆出 `ui/metadata_panel.py`、`ui/diagnostics.py`；app.py 里只剩流程编排 |

**流程代码刻意不搬**：Streamlit 的控件状态与「脚本每次重跑」的时序强耦合，
侧边栏取值、上传、解析缓存、卡片循环都留在 `app.py`，只搬自包含的函数与面板。

## 常见问题（FAQ）

### 1. PowerShell 报「因为在此系统上禁止运行脚本」，无法加载 `Activate.ps1`

**原因**：Windows 默认执行策略是 `Restricted`（禁止运行任何 `.ps1` 脚本），与本项目无关，也不是装错了东西。
用 `Get-ExecutionPolicy` 可确认；本项目机器的所有作用域都是 `Undefined`，即默认的 `Restricted`。

四种解法任选其一：

| 方案 | 命令 | 说明 |
| --- | --- | --- |
| **A. 不激活（推荐）** | `.\.venv\Scripts\python.exe -m streamlit run app.py` | 一个系统设置都不改 |
| B. 临时放行 | `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` 后再 `.\.venv\Scripts\Activate.ps1` | 只对当前这个终端窗口生效，关掉即恢复原样 |
| C. 永久放行当前用户 | `Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned` | 微软推荐的开发者设置；本地脚本可直接运行，从网上下载的脚本仍需数字签名；**不需要管理员权限** |
| D. 改用 cmd | 输入 `cmd` 回车 → `.venv\Scripts\activate.bat` | cmd 没有执行策略限制 |

### 2. 8501 端口被占用

换一个端口启动：

```powershell
.\.venv\Scripts\python.exe -m streamlit run app.py --server.port 8502
```

### 3. 项目统一约定

本项目所有命令统一写成 `.\.venv\Scripts\python.exe -m <模块>` 的形式，**不依赖虚拟环境激活**，从根上避开执行策略问题。

## 阶段 1 说明：卡片是怎么切出来的

解析流程（`pdf_parser.py` 负责，公式部分在 `formula_finder.py`）：

1. **取文本块（原子块）** —— 逐页用 `page.get_text("dict")` 取块，块基本对应自然段。
   同时做字符级修复：数学字母归一化、上下标转 Unicode、行尾断词拼接。
   **原子块一经生成就不再改写**（见下节「两层数据模型」）。
2. **拆出块首标题** —— 有些排版把小标题和它下面的正文归进同一个块，会把标题行单独拆出来。
3. **拆出独立成行的公式** —— 居中 + 数学字体 + 符号密度都满足的行单独成块，
   否则它会被当成正文粘进段落，后面所有基于块的公式判定都看不到它。
4. **判断单栏 / 双栏** —— 把每个文本块的横向范围投影到 x 轴上、按字符数累加覆盖量，
   双栏排版会在页面中部出现一条覆盖量明显偏低的竖直带，那就是中缝。
   （早期版本靠「左右各 ≥3 个块」判断，遇到某页左栏只有 2 个长块会漏判成单栏，
   于是左右栏文字被按 y 坐标混排，摘要和正文串成了读不通的句子 —— 已改为按文字量判断）
5. **重排阅读顺序** —— 双栏时以「通栏块」（大标题、摘要、跨栏图注）为分段点：
   通栏块之下先读完左栏，再读右栏。
6. **段落分组** —— 把被 PDF 拆成多块的同一段在**派生层**拼回去（原子块本身不动）；
   保守策略，宁可少合并也不错合并。
7. **切卡片** —— 超过上限的超长段落在句子边界切开（连字符断词会自动拼回）。
8. **识别标题** —— 综合字号（≥1.45 倍 → 一级）、加粗、章节名、编号四种证据。

**侧边栏开关**：段落自动合并、行尾连字符合并、单张卡片目标词数、默认展开卡片数。
改动任意一项都会自动重新解析（结果按「文件 + 设置」缓存，重复点击不会重算）。

**自查方法**：展开页面底部的「🔍 解析诊断」，对照 ① 每页排版检测、② 段落明细
（已按程序认定的阅读顺序编号）、⑦ 公式区域明细（列出每个区域合了哪几块）
和原 PDF，看顺序是不是「先把左栏读完，再读右栏」、公式有没有合错。

### 两层数据模型（原子块 + 段落视图）

这是本项目最容易被后续改动踩坏的地方，单独说明：

| 层 | 是什么 | 谁在读它 | 能不能改 |
| --- | --- | --- | --- |
| **原子块**（`Block`） | 从 PDF 提取出来的最小文本块 | 元数据、诊断、公式判定与聚类、图片关联 | **不可以**：任何阶段都不得改写它的 `text` |
| **段落视图**（`Paragraph`） | 由若干原子块派生出的自然段 | 内容角色分类、卡片构建、背景信息面板、界面 | 可以：它只是视图，写它不影响原子块 |

为什么要这么分：早期版本用一个 `merge_paragraphs()` **直接把后一块的文本塞进前一块**，
一旦公式碎片被并进散文，后面所有基于块的公式判定就再也看不到它了——
用户报的那个「第 9 页求和公式有一半留在句子里」正是这么产生的。
现在段落拼接是**纯派生**（`build_paragraph_groups` 返回分组索引 `[[0], [1,2], [3]]`），
公式判定前后各算一次：第一次供角色分类读整段文本，第二次把公式块单独摘出来。

### 已知限制（阶段 1）

| 现象 | 说明 | 计划 |
| --- | --- | --- |
| 图内文字标签偶尔被当成小标题 | 例如散点图里的 "Cursor C"。矢量图内的文字目前无法与正文区分 | 阶段 3 提取图片区域后一并处理 |
| 与正文同行的「行内小标题」不会单独成卡片 | 例如 "3.1.1 Task 1: Random Saccades. This task explored…" 标题与正文在同一行 | 暂不处理，保持行内阅读更自然 |
| 跨页的同一段落会分成两张卡片 | 分页处本身就存在语义断点 | 阶段 5 可考虑合并 |
| 整页大图的页面会显示「单栏」 | 页面上只有一侧有文字（另一侧是图），但阅读顺序不受影响 | 诊断标签措辞优化 |
| 扫描版 PDF 提不出文字 | 没有文字层，需要 OCR | 不在本项目范围内，会给出明确提示 |

## 阶段 2 说明：中英一键切换

### 怎么用

1. 把 `.env.example` 复制成 `.env`，在 `DEEPL_API_KEY=` 后面填上你的 Key
2. 启动应用，展开任意一张卡片，点里面的 **中文** 按钮 → 显示译文；点 **EN** → 回到原文
3. 侧边栏「🌐 翻译设置」里可以：切换后端、切换目标语言、**测试连接**、**清空翻译缓存**，
   并实时显示「API 请求 / 缓存命中 / 累计字符」计数
4. 改完 `.env` 不用重启服务，点侧边栏的「重读 .env」即可

### 实现要点

- **按需翻译**：只有你点了「中文」的卡片才会发请求，没点的不会消耗额度
- **缓存键 =（后端 + 目标语言 + 原文）**：同一张卡片来回切换只会请求一次；
  换后端或换目标语言才会重新翻译。缓存存在 `st.session_state`，关掉浏览器标签页即失效
- **失败不阻塞**：翻译出错时显示错误原因，同时继续显示英文原文，页面不会白屏
- **超时与重试**：单次请求超时 20 秒；超时 / 断网 / 429 限流 / 5xx 故障会自动重试 3 次
  （间隔 0.6s、1.2s），401/403（Key 不对）和 456（额度用尽）不重试，直接给出明确提示

### 额度

DeepL API Free 每月 **1,000,000 字符**。一篇 10 页双栏论文全文约 5 万字符，
所以满额约能翻 15~20 篇。侧边栏的计数可以随时核对有没有重复请求。

### 翻译报错对照表

| 提示 | 原因 | 怎么办 |
| --- | --- | --- |
| API Key 被拒绝（HTTP 403） | Key 填错 / 已停用 | 核对 `.env` 里的 `DEEPL_API_KEY`，注意免费版结尾要有 `:fx` |
| DeepL 本月免费额度已用完（HTTP 456） | 额度耗尽 | 等下月重置，或在 `.env` 里换 `TRANSLATOR_BACKEND=openai` |
| 连不上翻译服务 | 断网 / 代理 / 防火墙 | 检查网络，确认 `api-free.deepl.com` 能访问 |
| 翻译服务 20 秒内没有响应 | 网络慢或服务拥堵 | 直接重试 |
| 没有检测到任何翻译 API Key | `.env` 不存在或变量名为空 | 复制 `.env.example` 为 `.env` 并填 Key，再点「重读 .env」 |

## 阶段 3 说明：图片提取与侧边栏展示

### 怎么用

1. 上传 PDF 后，侧边栏底部出现「🖼️ 文献图片（N 张）」，缩略图**按页码分组**放在折叠面板里
2. 点缩略图下方的 **🔍 放大** → 主区域顶部出现「🖼️ 图片详情」，显示完整大图和元信息
   （原始像素、页面上显示尺寸、位置坐标、关联到哪张卡片），点「关闭大图」收起
3. 卡片标题上的 **🖼️×N** 标记表示：这张卡片附近有 N 张图（通常是图注那段文字）
4. 底部「🔍 解析诊断」第 ④ 节列出每张图的关联情况，第 ⑤ 节列出被跳过的图片及原因

### 实现要点

- **图片怎么找**：`page.get_images(full=True)` 拿到图片对象，`page.get_image_rects()` 拿到它在页面上的位置
- **透明背景**：科研示意图常带透明掩码（smask），代码会把掩码叠加成 alpha 通道，
  否则透明区域会渲染成黑块。颜色空间不是 RGB（如 CMYK）的会自动转换
- **内存策略（重要取舍）**：缩略图在解析时一次性生成（每张几十 KB）；
  **大图不预生成**，只在点「放大」时渲染那一张，并且只缓存最近 2 张。
  否则一篇带 20 张高清图的论文会把几百 MB 图片全塞进内存
- **关联方式**：取「同页 + 位置距离最近」的文本卡片，距离超过 140pt 或同页无文本就算关联不可靠。
  典型命中就是图片正下方的图注

### 已知限制（阶段 3）

| 现象 | 说明 |
| --- | --- |
| 矢量图画不出来 | 用线条和文字画出来的图（流程图、伪代码框、矢量坐标图）不是位图对象，`get_images()` 看不到它们。想覆盖这类图需要按区域渲染页面，属于阶段 5 的优化项 |
| 大图会被限制到 2200px 宽 | 原始 6000×4500 的图会等比缩小后显示（不失真，只是不放大到原始像素） |
| 关联是「位置最近」而非语义关联 | 跨栏大图可能关联到不相干的段落，需要人工核对（诊断面板里能看到距离） |
| 同一张图在多页重复出现会记多条 | 按「页面 + 位置」记录，便于按页浏览 |

## 阶段 4.1 说明：标题 / DOI / 摘要提取

### 怎么用

上传 PDF 后，页面**顶部**出现「📋 文献元数据」区：标题、DOI 各一个输入框，摘要一个多行框。
三者都可以**直接点击修改**，改动立即生效；每个字段下方标明**来源**，例如
「字号分析（17.2pt，第 1 页）」「第 1 页超链接」「摘要标题定位（Abstract）」。
点「↺ 用自动提取结果覆盖」可以把手动改过的内容还原。

提取失败时字段标题会变成「**标题（未找到，请手动输入）**」，不阻断使用。

### 三个字段各自的策略

| 字段 | 策略 | 依据 |
| --- | --- | --- |
| **标题** | 第一页做字号分析：取「标题区」（页面上部 55%）里字号最大的一行，把它上下紧邻的同字号行并进来（标题常折成 2~3 行）；用黑名单排除期刊名、栏目名（Report / Highlights / Authors / Copyright…） | 三篇样本的标题正好都是第一页字号最大的文字（14.3 / 17.2 / 18.9pt） |
| **DOI** | 按可靠性依次尝试：第一页超链接 → PDF 内嵌元数据 → 前两页正文正则。**全文正则很危险**（参考文献里几十个 DOI），所以只在「同一个 DOI 出现在前两页」时才采纳——那是页眉页脚，基本可断定是本文的 DOI | 三篇的 DOI 都在第一页超链接里，且都在前两页重复出现 |
| **摘要** | 先找摘要标题（Abstract / SUMMARY），再按阅读顺序往下收集，遇到 Keywords / Introduction / RESULTS / 版权行就停；**没有摘要标题的**（例如 ACM 的裸摘要）退化为「第一页第一段长正文」，并明确标注这是推测结果 | 三篇分别是：有 Abstract 标题 / 有 SUMMARY 标题 / 完全没有标题 |

### 实测准确率（三篇不同期刊的 PDF）

| PDF | 期刊排版 | 标题 | DOI | 摘要 |
| --- | --- | --- | --- | --- |
| `双栏.pdf` | ACM CHI'25（双栏） | ✅ 正确（17.2pt，两行合并） | ✅ `10.1145/3706598.3713992` | ✅ 正确 99 词（Abstract 标题定位） |
| `单栏.pdf` | ACM Games（单栏） | ✅ 正确（14.3pt） | ✅ `10.1145/3768627` | ✅ 正确 163 词（无标题，推测并标注） |
| `1-s2.0-...-main.pdf` | Cell Press / Current Biology | ✅ 正确（18.9pt，两行合并） | ✅ `10.1016/j.cub.2015.10.019` | ✅ 正确 219 词（SUMMARY 标题定位） |

**9/9 全部正确。** 但请注意：三篇样本恰好都是规范排版，**换一篇排版古怪的期刊仍可能出错**，
所以界面上的一切都可手动修正——这正是「准确性优先于自动化」的落地方式。

### 已知限制（阶段 4.1）

| 现象 | 说明 |
| --- | --- |
| 标题可能混入副标题或栏目名 | 黑名单只覆盖常见期刊用语，遇到不认识的栏目名（如 "Brief Communication"）可能漏掉 |
| 无标题摘要只能「推测」 | 程序取第一页第一段长正文，如果那一段是图注或致谢就会错，界面会明确警告 |
| 摘要可能多收 | 遇到不认识的结束标志（例如某些期刊用 "Highlights" 之外的词）会多收后面段落，界面会提示 |

## 阶段 4.2 说明：作者 / 第一作者 / 通讯作者 / 单位 / 附件链接

### 怎么用

上传 PDF 后，在「📋 文献元数据」里会多出这几组字段（全部可编辑、改动立即生效）：

- **第一作者 / 通讯作者 / 通讯邮箱**：三个单行输入框
- **作者列表**：多行文本框，**每行一位作者**
- **作者单位**：多行文本框，每行一个单位（保留原文的 ¹ ² ³ 编号）
- **附件链接**：多行文本框，每行一个 URL；下面会把每条链接渲染成**可点击的链接**，
  并注明它来自第几页、依据是什么
- 「📧 作者邮箱」折叠区：ACM 这类逐作者列邮箱的排版，会给出「姓名 <邮箱>」配对

每个字段下方都写着**来源**（例如「通讯标注段落（第 1 页）」「通讯邮箱反查（antti.oulasvirta@aalto.fi）」），
推测出来的值会带 ⚠️ 提示；右上角「↺ 用自动提取结果覆盖」可以把改过的内容一键还原。

### 提取策略（都是拿 6 篇不同出版社的论文摸出来的）

| 字段 | 怎么找 | 关键判据 |
| --- | --- | --- |
| **作者区** | 第 1 页标题下方、摘要标题（或第一段 ≥60 词的长正文）上方的所有块，**按纵向范围取** | 不能按阅读顺序取：ACM 的作者是三列网格，阅读顺序会把右栏作者排到左栏正文之后，按顺序切会漏人 |
| **作者列表** | 作者区里的短块拆成单个名字，**按版面坐标排序**（同一行按 x 从左到右） | 拆名前先去掉单位编号（`¹`、`^1,2`、`2,6`）；「`Yanxia Li School of Computer Science…`」这种名字与单位挤在一块的，在单位关键词处截断 |
| **单位** | ① 作者区里含 University / Institute / Department / School… 的块；② 第一页页脚**以编号开头**的小字块（Nature 把单位放在页脚） | 按编号标记（¹ ² ³ / 1 2 3）切条目；页脚那条要求「编号开头」，否则会把致谢和基金声明当成单位 |
| **通讯作者** | ① 显式通讯段落：`*CORRESPONDENCE` / `Corresponding Author:` / `Correspondence concerning… addressed to` / `Corresponding author at:`；② 由通讯邮箱反查（`antti.oulasvirta@aalto.fi` → Antti Oulasvirta） | **都没有就如实报「未找到」，绝不猜**（ACM 那篇就没有标注通讯作者） |
| **通讯邮箱** | 第一页 mailto 链接、通讯段落里的地址、`e-mail:` 标签后的地址 | ACM 那种逐作者列的邮箱**不算**通讯邮箱，只放进「作者邮箱」 |
| **附件链接** | 全页扫描 PDF 的链接注释 + 正文里印出来的 URL | 三重过滤：① 仓库域名（osf.io / github / figshare / zenodo / dryad / ICPSR…）或关键词直接命中；② 剔除出版社固定链接（许可协议、crossmark、期刊主页、本文 DOI）；③ 其余要求**上下文**里出现补充材料 / 数据可得之类的词。正文声明「有补充材料」但没有链接时，也如实记一条声明 |

基准答案是我逐篇打开第 1 页原始文本核对出来的，写进自动化测试做断言（41 条断言全过）：

| 样本 | 作者列表 | 第一作者 | 通讯作者 / 邮箱 | 单位 | 附件链接 |
| --- | --- | --- | --- | --- | --- |
| Elsevier（JESP） | 5/5 ✅ | ✅ | Diane Pecher ✅ | ✅ 1 条 | OSF ✅ |
| SAGE（PSPB） | 5/5 ✅ | ✅ | Douglas Martin ✅ | ✅ 2 条（¹²） | OSF ✅ + 声明 |
| **ACM（CHI，三列网格）** | 5/5 ✅ | ✅ | **未找到**（该刊未标注）✅ | ⚠️ 3 条散块 | 无 ✅ |
| Frontiers | 3/3 ✅ | ✅ | Analicia K. Howard ✅ | ✅ 4 条（¹²³⁴） | 5 条（含 OSF、数据 DOI、补充材料页）✅ |

### 已知限制（阶段 4.2）

| 现象 | 说明 |
| --- | --- |
| ACM 三列网格的「单位」是散块 | 名字与单位在同一行交错，程序按块去重后给出去重列表，**需要人工核对**（作者列表本身是准的） |
| 通讯作者可能「未找到」 | 有些期刊（如 ACM）压根不标注通讯作者，程序如实报告并给出各作者邮箱，不猜 |
| 附件链接的**分类**可能偏差 | 「补充材料 / 数据与代码 / 预注册」是按域名与上下文关键词判的，界面会给出页码与依据，链接本身是原文里抓的，可直接点开核对 |
| 作者名里的重音、连字符 | 按原样保留（`Renée`、`Jean-Luc`）；比对时做归一化，不影响通讯作者匹配 |
| 单位与作者的**对应关系**没做 | 本轮只给「单位列表」（保留 ¹ ² ³ 编号）+ 作者名上的编号，人工可对上；自动映射见阶段 4.3 的说明 |

## 阶段 4.3 说明：GROBID 交叉校验（把外部模型当「第二意见」）

### 怎么用

1. **启动 GROBID**（完全本地，不需要梯子、不需要登录）：

```powershell
docker run --rm --init --ulimit core=0 -p 8070:8070 grobid/grobid:0.9.1-crf
```
看到 `Started oejs.Server@…{STARTING}…@384ms` 就说明服务起来了（之后它加载模型时不再刷日志，看着像卡住是正常的）。
**验证**：另开一个窗口 `curl.exe http://localhost:8070/api/isalive` 返回 `true`。
**停止**：在那个窗口按 `Ctrl+C`（容器带 `--rm`，停掉自动清理）。

**后台运行（可选，不开日志窗口）**：把 `--rm --init` 换成 `-d --rm --name grobid --init`：

```powershell
docker run -d --rm --name grobid --init --ulimit core=0 -p 8070:8070 grobid/grobid:0.9.1-crf
docker ps                       # 看是否在跑
docker logs -f grobid           # 看日志（Ctrl+C 退出查看，不影响容器）
docker stop grobid              # 停止（--rm 会自动清理容器）
```

2. **上传 PDF**，在「📋 文献元数据」下方会出现 **「🔍 GROBID 交叉校验」** 面板：
   - 服务在 → 自动跑一次校验（约 1~3 秒，结果缓存在会话里），显示逐字段对比表；
   - 有差异的字段带「**一键采信**」按钮：单值字段直接采用 GROBID 的值；
     列表字段是「**只补空、不覆盖**」——GROBID 独有的条目追加进去，本地已有的保持不动；
   - 服务不在 → 面板只显示一句提示 + 上面那条启动命令，**不影响任何阅读功能**。

3. 换服务地址：设环境变量 `GROBID_URL`，默认 `http://localhost:8070`。

### 为什么这么设计

| 决策 | 理由 |
| --- | --- |
| 只当「第二意见」，**不自动合并** | 用户定下的原则是准确性优先：不做黑箱合并，只给「结论 + 一键采信」，最终由人拍板 |
| `consolidateHeader=0` | 不让 GROBID 偷偷联网查 Crossref——既避免网络依赖，也保证对比的是**它自己的抽取能力** |
| `includeRawAffiliations=1` | 单位优先取 PDF 原文字符串（`raw_affiliation`），比模型切碎的 `orgName` 更完整 |
| 比对前先归一化 | 大小写、重音、序号（¹²³）、标点、空白都不算差异，否则「Steve van Pelt / Steve Van Pelt」会被判成冲突，白白制造焦虑 |
| 列表「只补空不覆盖」 | 本地规则在某些版式上更干净（见记分卡），整段替换会把本地的好结果冲掉 |
| 面板上列出 GROBID 的出错案例 | 避免用户盲信外部模型 |

### 记分卡（9 篇、6 个出版社，本地 GROBID 0.9.1 CRF 镜像）

GROBID 一侧取自**落盘的真实 TEI 响应**，所以这份记分卡可离线复现；比对口径已归一化。

| 字段 | 两边一致 | GROBID 更多/更全 | 内容不同 | 只有一边 |
| --- | --- | --- | --- | --- |
| 标题 | **8/9** | 0 | 1（Nature：GROBID 把标题抽成了期刊名） | 0 |
| DOI | **9/9** | 0 | 0 | 0 |
| 摘要 | 3/9 | 2 | 3 | 1（Cell Press：本地 219 词、GROBID 0 词） |
| 作者列表 | **6/9** | 3（多出来的都是噪声，见下） | 0 | 0 |
| 第一作者 | 7/9 | 0 | 2（GROBID 的第一作者是题记人名 / 编者） | 0 |
| 作者单位 | 0/9 | 4 | 5 | 0 |
| 作者邮箱 | 4/9 | 0 | 5 | 0 |

**人工判定（重要：自动比对只能告诉你「哪里不一样」，判断不了「谁对」）**

| 差异 | 人工结论 |
| --- | --- |
| 作者列表：SAGE 多 `George Washington`、Frontiers 多 `Wolnei Caumo`/`Ariadne Brandt`、xlm 多 `Jane Kelly` | **GROBID 错**：分别是题记里的人名、侧栏的编者与审稿人、把 `Laura Jane Kelly` 拆成两半。**本地规则 9/9 作者都正确** |
| 标题：Nature HB | **GROBID 错**（抽成期刊名 `nature human behaviour`），本地正确 |
| 摘要：Cell Press | **GROBID 错**（该刊摘要叫 SUMMARY，它认不出、返回 0 词），本地 219 词正确 |
| 摘要：单栏 / ACM 网格 vs 双栏 / SAGE | 前者 GROBID 更全、后者本地更完整——**摘要字段两边都会失手，建议人工核对** |
| 作者单位 | **GROBID 通常更干净**（会合并被版面切碎的院系名、剥掉序号）；本地更贴原文。**这个字段差异最多，务必人工核对** |
| 作者邮箱 | 口径不同但互补：本地覆盖「作者区逐作者列邮箱」的排版（ACM 那类）+ 通讯邮箱；GROBID 覆盖 PDF 头部里的邮箱 |
| ORCID | **只有 GROBID 提供**（本地不做），界面上作为附加行显示 |

**结论**：本地规则在标题、作者列表、作者去噪上更强；GROBID 在**结构化**（每位作者的邮箱与 ORCID、单位归一化）上更强。两者互补——这正是交叉校验的价值。

### 这次交叉校验替本地规则抓出的 4 个真实缺陷（已修）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 单栏.pdf（ACM Games）作者数 **0** | 作者名与单位挤在同一块（`LLOGARI CASAS, 3FINERY LTD, …`），本地看到单位词就整块丢弃 | 切出「第一个逗号之前、单位关键词之前」的那段当候选人名 |
| 双栏.pdf（ACM CHI）作者数 **6**（实际 5） | 院系名 `Media Engineering Technology` 不含单位关键词、又被版面切成单独一块，通过了人名判据 | 新增「整串 token 都是学科词」的否决规则（判据是**全部**而非**含一个**，避免误杀 `Andrew Law`） |
| Cell Press 少 1 位作者 | 重音被排版拆开（`Ange ´lina Vernetti` 实为 Angéline），含重音的姓名整段判不出 | 把「字母 + ´ + 空格」合成组合尖音符再做 NFC；名字校验从 ASCII 扩到 Unicode 字母 |
| Cell Press 单位 **0 条** | 该刊把单位放在**第 2 页**，本地只找第 1 页 | 单位池扩到「第 2 页里以编号开头且含单位关键词的小字块」 |

修完这 4 处后，作者列表与 GROBID 一致的样本从 3/9 提升到 6/9（其余 3 篇是 GROBID 混入噪声）。

### 已知限制（阶段 4.3）

| 现象 | 说明 |
| --- | --- |
| 上传后多花 1~3 秒 | 服务在时会自动跑一次校验（结果缓存，同一文件不重复调用）；嫌慢可以改成只在点按钮时跑 |
| 首次调用更慢（约 5~10 秒） | GROBID 启动后第一次调用要加载模型 |
| **用的是 CRF 轻量镜像** | 500MB 的 `-crf`（纯 CPU）；官方另有 8GB 的 `-full`（深度学习模型，Windows 容器不支持 GPU、只能 CPU 跑且慢很多），只有在需要更准的参考文献/引用解析时才值得换 |
| 单位字段几乎总是不一致 | 两边切分格式不同，属正常；界面已标出差异，人工核对即可 |
| GROBID 也会出错 | 实测失效模式：标题抽成期刊名、把题记/编者/审稿人当作者、SUMMARY 式摘要抽不到。**不盲信任何一边** |
| 依赖 Docker | GROBID 走 Docker 分发（官方推荐）。不启动它时所有功能照常，只是少一个第二意见 |

## 阶段 4.4-A 说明：通讯作者的「图标标记」（信封图标）

### 为什么做这一步

有些期刊**根本不写** "Corresponding author" 这类文字，只在通讯作者名字后面画一个
**小信封图标**。例如 npj Digital Medicine 那篇（`测试pdf\4.3测试\`）：

| 证据 | 位置 |
| --- | --- |
| 灰色信封矢量图 ×2 | 作者行 `y≈262`，`x≈349`（`Wei Liu` 后）、`x≈419`（`Shuang Liu` 后），各 9.2×7.0pt、23 个绘制项 |
| 页脚 mailto ×2 | `lance1971@163.com`、`shuangliu@tju.edu.cn` |

图标既不是文字也不是图片对象，是**矢量绘制**——只看文本的规则永远发现不了它，
于是这两位共同通讯作者在 4.4-A 之前一直是空的。

### 怎么判（`find_icon_marked_authors`）

| 判据 | 做法 |
| --- | --- |
| ① 位置与大小 | 图形落在**作者行纵向带子**内、边长 4~20pt（带子外是页眉徽标、CrossMark「Check for updates」图标） |
| ①b 形状必须是「复合图形」 | 绘制项 ≥ 6 且含直线/矩形——**排除纯曲线的圆和单个方框**（见下面那次误判） |
| ② 左邻文字 | 图标左边 8pt 内、纵向有重叠的文字里，**最后一个**能解析成人名的就是被标记的作者（名字与上标编号常被排成两个 span，所以连续向左并最多 4 段） |
| ③ 只认作者列表里的人 | 且同一位作者只记一次 |

配对邮箱时**先按「邮箱本地部分含该作者姓名」匹配**（`shuangliu@…` → Shuang Liu），
匹配不上再按图标与页脚的**左右顺序**依次配对；同一个邮箱不会配给两位作者。
每一项配对依据都写进备注，人工一眼能看出是怎么来的。

### 回归工具抓到的一次真实误判（已修）

第一次跑 `回归检查.bat` 时，10 篇里有 **2 篇**变了——一篇是想要的 npj，另一篇
（Nature Human Behaviour `s41562-026-02534-0.pdf`）把 **3 位作者**都判成了通讯作者：

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 通讯作者变成 `Yunpeng Bai、Shengdong Zhao、Antti Oulasvirta`，邮箱还被重复配了两次 | 作者名后有 **3 个黑色 ORCID iD 圆形徽章**（4 段纯曲线的圆 + 几块 <4pt 的白色镂空字母），被当成了信封 | 加「复合图形」判据；邮箱配对加去重 |

顺带发现：该样本的真信封图标与左侧名字之间隔了 **9.2pt**（上标 `2,6` 前有薄空格 U+2009），
超过 `ICON_GAP_PT=8.0`，所以这一支**如实弃权**，改由原有的「邮箱反查」给出
`Antti Oulasvirta`——结果与加本功能之前**完全一致**（回归比对 10 篇全绿）。
宁可弃权也不放宽间距去硬认：放宽会把「图标左边更远的另一位作者」认成被标记者。

### 实测

| 样本 | 结果 |
| --- | --- |
| npj Digital Medicine | 通讯作者 `Wei Liu、Shuang Liu`；通讯邮箱 `lance1971@163.com、shuangliu@tju.edu.cn`；第一作者 `Minghao Du` 未受影响 |
| 回归比对（10 篇） | 9 篇与基线**完全一致**，仅 npj 这篇出现**预期内**的 2 处差异 |
| 验收脚本 | `python tests\test_corresponding.py` → 通过 17 · 失败 0（含 Nature、Elsevier 两个负例） |

### 已知限制（阶段 4.4-A）

| 现象 | 说明 |
| --- | --- |
| 只认**右邻**图标 | 少数期刊把图标放在名字前面，这类仍识别不到（会退化成邮箱反查，不会给错） |
| 图标与名字间距 > 8pt 时弃权 | 见上面的 Nature 案例：宁可不判，也不猜 |
| 只查第 1 页作者行 | 作者行在首页是绝大多数情况；封面页在别处的样本识别不到 |
| 位图图标仍较少见 | 判据同时接受小图片（`get_image_info`），但目前只在小矢量图上验证过 |

## 阶段 4.4-B 说明：表格区域识别（整张表截图为图）

### 为什么做这一步

期刊表格在 PDF 里**没有任何「表格」标记**，只有一堆带坐标的文字。4.4-B 之前它们被
当成正文按阅读顺序线性化，卡片里于是出现这样的句子（npj 第 4 页表 2 的原文）：

```
EV 0.758 0.682 0.735 0.707 0.723 0.746 0.790
Fusion EV-EI-FC 0.960 0.882 0.905 0.949 0.924 0.931 0.977
```

列与列的关系全丢了：读者既看不出这是表格，也不知道 `0.758` 属于哪一列，还白占了
卡片流上百词的篇幅。现在这些区域整块截成图片（**与公式共用同一条截图管线**）。

### 判据：① 题注锚点 + ② 对齐列几何校验，缺一不可

| 判据 | 内容 |
| --- | --- |
| ① 题注锚点 | `Table 2 \| …` / `Table 1: …` / `TABLE 1 …` 这类题注行（`table_finder.CAPTION_RE`） |
| ② 几何校验 | 题注下方必须构成 **≥3 列 × ≥3 行**的对齐网格（列 = 出现在 ≥3 行里的 x 位置） |
| ③ 单元格形状 | 中位单元格 ≤6 词，或数字占比 ≥30%——挡「多栏正文 + 附近恰好有一句 Table N」 |
| ④ 排除 | 页眉页脚 / 参考文献 / 版权页里的行不参与；已确认的公式区域不参与 |

**为什么必须有第②步**：实测三篇样本的正文里都有以 `Table N. ` 开头的提及句——

| 样本 | 提及句 | 下方的几何 |
| --- | --- | --- |
| npj 第 2 页 | `Table 1. Independent-samples t-tests indicated no group differences in…` | 两栏散文 → 只有 2 个对齐位置 ✗ |
| SAGE 第 15 页 | `Table 7 for cell values including Target Sex). The analysis…` | 两栏散文 ✗ |
| Frontiers 第 6 页 | `Table 1. An overview of these loadings is summarized below.` | 两栏散文 ✗ |

只认题注这三处会全部误判；几何校验一眼就能分开。

### 一个关键实现细节：判据写在「行」层，不是「块」层

实测（表格一行 = 同一 y 上的多个独立文本行）：

| 样本 | 一行的单元格数 | Block 层的样子 |
| --- | --- | --- |
| npj Digital Medicine | 8 个独立行对象 | **被合并成一个块**，列位置信息丢失 |
| Nature Human Behaviour | 7 个 | 同上 |
| ACM CHI | 4 个 | 同上 |

所以新增 `pdf_parser.extract_page_lines()` 单独采集行级数据，判定完再按坐标把行映射回块。
（实现上它与块级解析**共用同一次 `page.get_text("dict")`**：分成两次解析的话，
多表样本的解析耗时会多出 1.7 秒——实测双栏.pdf 从 2.27s 涨到 3.98s，纯属白跑。
现在表格判定的耗时增量在噪声范围内，10 页样本约 +0.03 秒。）

### 开发中踩到的 8 个坑（全部已修，都有回归守着）

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 表格图把后面整段正文也框了进去（npj 词数掉了 1571） | 表格下方第一行正文的左边界与第一列几乎重合，被当成「单元格内换行」**一路链式**并进最后一行 | 合并加三道闸门：只并短行（≤8 词）、不并句末标点结尾的行、距离按**该行自己的 y** 算 |
| 同上（修完仍掉 1571 词） | 双栏排版里**左右两栏正文行 y 相同**，被当成「一行两个单元格」 | 表格行要求 **≥3 个单元格**（双栏正文恰好 2 个） |
| 同上（修完仍不干净） | 与表格同 y 的右栏正文行反复出现，竟被**投票**成了一个「合法列」（x≈306 拿到 5 票） | 按**栏位**过滤：只取与题注同栏的行（通栏行一律允许） |
| ACM 6 张表只认出 1 张 | 表题注与表体之间隔着一条横线 + 空行，实测间距 **39pt**，超过当时设的 34pt | `CAPTION_GAP_PT` 放宽到 48（是不是真表格由几何校验把关，不靠间距） |
| 加上「每格都必须短」的守卫后，Nature 的表和 ACM 表 4 全部消失 | 真表格里也有 `P value, effect size (95% CI)` 这种长单元格 | 改成看**中位**单元格长度，不看每一格 |
| Nature 第 4 页的一张**六面板图**被当成表格（覆盖 66 个块） | 坐标轴刻度标签同样是「一行好几个短单元格 + x 对齐」 | 无题注兜底路径额外要求**行距规整**（表格行距均匀，图的标签疏密不均） |
| Nature 的表识别出来了，卡片里却一张图都没有 | 表题注加粗、字号略大，被角色分类判成 `heading`，先走了标题分支 | 表格分支排在标题分支**之前** |
| 参考文献区里的一张表被识别、却永远不显示 | 排除角色写成了 `references`，而实际常量是 `reference` | 角色名与 `pdf_parser.ROLE_*` 逐字对齐 |

### 怎么用 / 怎么核对

- **默认：截图呈现**。卡片里表格位置出现一张整表的图，图下有题注小字；
  中文视图下表格**保持原图**（与公式同一策略，不参与翻译）。
- **侧边栏「表格呈现 → 保留文字」**：切回 4.4-B 之前的行为（表格文字线性留在卡片里）。
  已用 10 篇样本验证：这个开关只影响「表格」，其余字段与截图模式完全对应；
  表格区域的文字会回到卡片流，**并且表格区域不会参与公式判定**
  （否则表格里的 `β = 13.85` 这类单元格会被聚成一张公式图，在表格文字中间冒出一张图）。
  （切换会重新解析，约 1~3 秒。）
- **诊断面板第 ⑧ 节**列出每个表格区域的页码、行×列、**表注行数**、区域范围与成员块，
  可用来核对「框得准不准」。
- **「显示全部内容」模式**里表格按**原文字**列出（不是截图）——这个模式的用途是核对分类，
  在那里能直接看到表格的线性文字、也能复制里面的数字。
- 截图可点开放大；表格图不参与词数统计与翻译。

### 用户验收反馈的两处修复（2026-09-15）

第一轮验收时报了两个问题，都已修好并有回归守着：

**① 表格图最底部缺一截** —— 缺的是**表注**。表注（缩写说明
`EV Emotion variation, EI Expression Intensity…`、显著性说明
`Bold values indicate the best performance.`、`Note: Eye dominance…`）
在行层只有 1 个单元格，被「表格行必须 ≥3 格」的规则排除掉了。

| 判据 | 取值 | 理由 |
| --- | --- | --- |
| 紧贴最后一行 | ≤13pt | 表注就贴在表格下沿 |
| 行距 | ≤12pt | 多行表注（Frontiers 有 3 行）要一起收 |
| **字号小于正文** | ≤0.92×正文 | 关键判据：正文段落同样紧跟在表格下方（npj 表 1 下面就是 123 词正文段），只按间距会把正文吞进来 |
| 落在表格横向范围内 | 允许左偏 12pt | 表注常比表体多缩进几个点（Frontiers 实测 9.4pt） |

结果：npj 4 张表、ACM 表 3、Frontiers TABLE 2、Nature 表 1 的截图底部都补齐了，
诊断面板第 ⑧ 节新增「表注行」一列可核对。

**② 比较多的公式没有被截图** —— npj 第 8、9 页的显示公式被排成**上下叠放的碎片**
（分数的分子/分母各是一块），全部只有 weak/fragment 等级、**没有强候选当种子**，
聚类从不启动。更麻烦的是这些公式的等号被字体错映射成了 `¼`
（`Cði; jÞ` 里的 `ð Þ` 是括号），线性文本本身就是乱码。

| 修法 | 说明 |
| --- | --- |
| **碎片堆当种子** | 同一页同一栏、y 区间重叠或 ≤6pt 的公式候选块，只要整堆里有一块带**大运算符或比较符**，就把这堆当一处公式（挑一块提升为强候选，其余被聚类吸收） |
| **字形错映射修复** | `¼ → =`、`ð Þ → ( )`，只在「同一行出现上下标」的数学语境里替换（实测 `Σ_{t=1}^{N}` 里的 `ₜ_¼₁` 正是 t=1，反过来印证了 ¼ 就是等号）。第一版没卡这个条件，把正文里的 `about ¼ of the trials` 改成了 `about = of the trials`，所以必须限制语境 |
| **收紧边界** | 证据只看**运算符**，不看上下标、也不看字母个数：Nature 那篇的模型图有 9 组子图标签（`A₁ O₂ B₁ B₂`、`C₁ U`、`S₂ S_F`），图例/坐标轴文字（`Human, high K`、`30 s 60 s 90 s`、`Policy π`）同样够长——只认上下标时 Nature 会凭空多出 11 个「公式区域」 |

结果：npj 公式区域 **1 → 4**（都是第 8、9 页的真公式）；
Nature 仍是 3 处、单栏仍是 32 处、其余样本不变——**改动只落在漏检的那几处**。

**第二轮验收又报了一处**（同页的另一处分数：`= C(i; j) P` / `P i; j` / `ₖ C(i; k)`），
排查后发现两个更细的原因，都已修（v0.4.7）：

| 现象 | 根因 | 修法 |
| --- | --- | --- |
| 这处公式一直没出图 | 它的 `¼` 与错映射的 `ð Þ` **分属两行**，而字形修复的语境门槛当时写在**行**那一层——逐行看谁都不满足条件，等号一直没修回来 | 门槛与替换都移到**块**这一层（跨行才看得全） |
| 同一处仍不成立 | 它的等号因为阅读顺序被排到了**块首**（`¼ C(i; j) P`），而旧正则要求「`¼` 前面有字符」→ 直接不匹配 | 去掉 lookbehind，改由「同一行/块里必须有上下标或错映射括号」把关；已加断言防止误伤正文里的 ¼ |
| 卡片里残留 `\x01 \x03` 这类乱码块 | 它是公式里被错映射成控制字符的符号，没有公式等级、不被吸收，却本来就落在图片范围内 | 聚类末尾收编**完全落在区域矩形内**的极短块（≤3 词、正文角色），乱码不再留在文字流里 |

结果：npj 公式区域 **4 → 5**，其余 9 篇样本与基线**完全一致**（改动零外溢）。

**第三处是主动扫描发现的**（第 9 页整行公式 `sᵢ = {sᵢ(1); …}` 与 `sⱼ = {sⱼ(1); …}`
被排成相邻两块，其中一块没有公式等级，碎片堆因此凑不满两块 → 不出图，v0.4.8 修）。
修法是把「碎片堆」的候选池扩到「看起来像公式半行」的块，但**必须同时加四道闸门**：

| 闸门 | 为什么 |
| --- | --- |
| 短（≤24 词） | 正文句子动辄 15~20 词 |
| 不是散文 | 复用已有的虚词判据 |
| **符号密度 ≥18%**（括号 / 分号 / 运算符 / 上下标占比） | Cell Press 的正文句 `² = 0.16), demonstrating that…` 也有等号，但符号占比只有 5% |
| 不是表格块 | Nature 表格每行都有 `β = 13.85` |

**这一步的教训（实测数据）**：第一版只加了「有等号或大运算符」就往池子里放，
结果 Cell Press 公式区域 0 → **3**、Nature 3 → **6**、单栏 32 → **30**（正文句与
表格单元格全被拉进来了）✗；补上四道闸门后所有样本回到原值，只有 npj 增加 1 处。
**放宽召回时必须同时加精度闸门，并用全样本基线验证"零外溢"**。

最终：npj 公式区域 **6 处**，这篇里再没有「是公式候选却没进区域」的块；
其余 9 篇样本与基线始终完全一致。

### 另一处验收反馈：DOI 被当成卡片小标题（v0.4.9）

用户报：「前 7 张卡片有把 doi 识别成小标题的 bug」。实测两个成因：

| 成因 | 实测 | 修法 |
| --- | --- | --- |
| DOI 行被并进标题块 | npj 第 1 页 DOI 行（8pt）紧贴论文大标题（25.9pt）上方，两者被排进同一个块 → 整块成了卡片一级标题；Nature 更复杂：`Article`(10pt) + DOI(8pt) + 标题(26pt) 三行一块 | 新增 `_split_leading_metadata`：**以 URL/DOI 为主**的前导小字行拆出来单独成块 |
| running head 的 DOI 被判成章节标题 | DOI 行字号小但常加粗，触发「加粗 + 字号≥正文 0.95 倍」→ 三级标题；期刊页眉上的 DOI 因此混进多张卡片（用户看到的「前 7 张」） | URL 占比 ≥45% 的文本不当标题；页面顶部 20% 内的 URL 块直接归页眉/封面信息 |

**两个必须守住的边界**（都实测踩过，被回归工具与 `测试` 抓住）：

| 边界 | 不加会怎样 |
| --- | --- |
| 拆前导行必须要求「前导段以 URL/DOI 为主」 | 图注、表格里「小字标签 + 大字数值」的块也被拆开 → 9 篇样本的卡片结构全变（改动必须零外溢） |
| 「第 1 页标题之上」要按**标题带**判断（最大标题 + 同号近邻），不能只取字号最大的那一块 | ACM CHI'25 的大标题被排成两块（`…Slow Noticing in Food` 17.0pt 与 `Gardens` 17.2pt），第一行被误判成「标题之上」踢出卡片 ✗（回归工具在提交前抓到） |

最终：npj / Nature / Frontiers 三篇按预期变化（DOI 行移出卡片、标题块不再含 DOI），
其余 7 篇与基线**完全一致**。

## 阶段 3.5 说明：卡片流净化与「论文背景信息」

### 为什么做这一步

早期版本把 PDF 里所有文本块都当正文排进卡片流，于是页眉页脚、作者单位、期刊栏目名、
参考文献全混了进来。三篇样本的实测：

| 样本 | 全部文本块 | 属于非正文 | 占比 |
| --- | --- | --- | --- |
| `单栏.pdf` | 203 | 44 | 22% |
| `双栏.pdf` | 198 | 47 | 24% |
| Cell Press | 107 | 48 | 45% |

而且正文卡片里 30%~45% 不足 20 词（最短 1 词），读起来全是碎片。

### 现在的做法

**① 内容角色分类**（`classify_roles`）——每个文本块判定一个角色：

| 角色 | 判定依据 | 去向 |
| --- | --- | --- |
| 正文 | 剩下的都算 | 阅读卡片 |
| 章节标题 | 字号 / 加粗 / 编号 / 章节名 | 卡片内加粗显示 |
| 图注 | `Figure 3.` / `Table 2:` 这种「编号 + 标点」开头 | 阅读卡片（按你的要求视作正文） |
| 页眉页脚 | 跨页反复出现的短文本（去掉数字后比对） | 背景信息 |
| 作者与单位 | 第 1、2 页里「标题与摘要之间」的短块 | 背景信息 |
| 封面页信息 | 某页没有长正文时整页（Cell Press 那种导读版面） | 背景信息 |
| 版权 / 许可 / 资助 | ©、licensed under、grant agreement… | 背景信息 |
| 参考文献 | `References` 标题及其后的全部内容 | 背景信息 |
| 栏目名 / 标签 | Authors / Highlights / CCS Concepts / Report / 图内面板标签 | 背景信息 |

**② 卡片按阅读顺序聚合到 100~300 词**（`build_reading_cards`）

- 侧边栏「卡片目标词数」默认 200（攒到这么多词就收一张卡），实际落点 **100~300 词**
- **章节标题进卡片内部、加粗显示**，不再单独占一张卡——否则像 CHI 那种小节特别多的
  论文，每张卡都只有一两百词，凑不到目标长度
- 卡片不会跨「非正文」区域，所以不会把互不相干的两段粘在一起
- 章节末尾的零头能并进上一张就并；再超上限就先收卡，保证卡片不超过 300 词

**③ 卡片标签**：`#7 · §3.1 Task → 3.3 Determining Eye Dominance · 原文第 3–4 页 · 335 词`

**④ 论文背景信息面板**：4 个折叠分组 —— 作者与单位 / 期刊信息与栏目 / 参考文献 / 页眉页脚。

**⑤ 「显示全部内容」开关**（侧边栏）：打开后不再过滤，非正文也照原样列出来并标注角色，
用于核对过滤有没有误杀真正文。

### 实测效果

| 样本 | 卡片数（净化前 → 后） | 词数中位 | 落在 100~300 | 20 词以下的碎片 |
| --- | --- | --- | --- | --- |
| `单栏.pdf` | 203 → **25** | 227 | 25/25 | 59 → **0** |
| `双栏.pdf` | 198 → **26** | 242 | 25/26（最大 306） | 39 → **0** |
| Cell Press | 107 → **16** | 248 | 16/16 | 15 → **0** |

### 公式与统计量的处理

统计量是科研阅读的重点，但 PDF 里的数学排版会以三种方式坏掉：

| 问题 | 现象 | 处理方式 |
| --- | --- | --- |
| **数学字母符号** | `𝑇 𝑣 𝑥`（U+1D400 数学字母区）既难读、也翻译不了 | 用 NFKC 归一化成普通字母 `T v x`（单栏样本里修掉了 463 个字符） |
| **上标被拆成两块** | `ηp² = 0.16` 被切成：前块结尾 `…p = 0.021, hp`、后块开头 `2 = 0.16), …` | ① 靠「字号更小 + 底边高于本行其他字符」判断上标（**这些 PDF 的 flags 上标位根本没设**），转成 Unicode 上标 `²`；② 放宽段落合并规则，把跨块的上标粘回去 |
| **希腊字母被字体错映射** | `η` 提取出来是 `h`，于是 `ηp²` 成了 `hp²` | Cell Press 用「单字形子集字体」画 η，字体里字形名都被改写成 "LATIN SMALL LETTER H"，信息已彻底丢失。只能在统计量上下文按模式修：`hp² =` / `hp² <` → `ηp²`。这类修复按需追加，遇到新符号告诉我即可 |

实测现在能完整正确地带出：`F(1, 31) = 5.92, p = 0.021, ηp² = 0.16)`。

**公式的呈现方式（已实现：区域截图）**

先说结论：**PDF 里没有 LaTeX / MathML 源码可提取**。实测翻了 6 篇样本的全部内部对象（解压后逐流搜索）：

| 检查项 | 结果 |
| --- | --- |
| MathML 标签 `<math>` | 0 个对象 |
| LaTeX 命令 `\frac` `\begin{` `\sum` | 0 个对象 |
| OMML（Word 公式） | 0 个对象 |
| 结构树 `/StructTreeRoot` | 只有 2 篇 tagged PDF 有，且里面只有**图片 alt 文本**和**软连字符**，没有公式源码 |

原因很直白：Obsidian 之类能渲染二维公式，是因为源头是 Markdown 里的 LaTeX 源码；**PDF 是「印刷成品」，排版源码早就丢了**，公式只剩下一堆带坐标的字形。所以二维公式（分式、积分、矩阵）**无法用文本表达——这是信息维度问题，不是实现难度问题**。

因此采用**区域截图呈现**：把同一处公式的碎片聚成一个「区域」，整簇渲染成一张图。

**① 三级判据**（`formula_finder.py`，只用符号锚点，不用词锚点）

| 等级 | 判据 | 允许做什么 |
| --- | --- | --- |
| **强候选** strong | 打分 ≥4 且通过全部防线 | 单独成图；可作为区域聚类的**种子** |
| **弱候选** weak | 打分 2~3，或打分够但没过防线（降级，**不会**落回普通文字） | 只能被区域吸收；只有「相对所在栏有缩进 + 数学字体 + 括号配对」时才允许当种子 |
| **公式碎片** fragment | 词数 ≤6、无句末标点、非散文，且含数学锚点/上下标/数学字体/单字母变量 | **只能被区域吸收，绝不单独成图**（这是「不把半句话变成图片」的关键） |
| 普通文字 | 其余 | 留在正文里、照常可选中可翻译 |

打分规则：大运算符（`∑ ∏ ∫ ∮ √ ∂ ∇ ∞`）**+3**（近乎无噪声的强信号，仅凭它就能抬成强候选）；
比较运算符 +2；上下标 +2；其它数学运算符每出现一种 +1（最多 +2）；词数 ≤10 再 +1。
防线（只限制「单独成图」，不限制被吸收）：必须有变量名、比较运算符两边必须有操作数
（挡 `"<.001"` 这类表格碎片）、括号必须配对、必须相对所在栏有缩进
（正文段落一律从左边界起排，天然被排除）。

**② 区域聚类**：以强候选（合格的弱候选）为种子逐轮生长，满足任一条件就吸收一个公式候选块——

- 与当前区域外接矩形的间隙 ≤ max(8pt, 1.2 × 簇内中位字号)（约 12.6pt，与旧版口径相当）
- x/y 投影重叠 ≥30%，且**另一方向上确实相邻**（间隙 ≤ 同一阈值）
- 与簇在同一行上（y 重叠超过较矮者的一半，同栏）

散文永远吸不进来（只有公式候选能进）；单簇上限 15 块、面积 ≤ 页面 20%。
**算法清单走确定性规则**：从 `ALGORITHM 1: … / Input:` 这类真正的清单标题出发，
把连续的行整簇收进来（不受块数上限约束），并对行数、缩进做限制以免吞到正文段与页脚。

**③ 渲染**：`page.get_pixmap(clip=区域, dpi=200)`，按需渲染 + 会话内缓存。
公式出现在卡片里**原文对应的位置**上，视觉 100% 保真；代价是不可选中。

实测（6 篇不同期刊的样本，含单/双栏、Cell Press、Nature Human Behaviour、Frontiers、SAGE、ACM、xlm）：

| 样本 | 公式区域 | 说明 |
| --- | --- | --- |
| 单栏.pdf（ACM Games，16 页） | **32 个** | 含 4 个算法清单（每个整张图，含 Input/Output 与全部编号行） |
| 双栏.pdf（ACM CHI'25） | 1 个 | 该文只有一处显示公式 |
| Cell Press《Current Biology》 | 0 个 | 心理学论文只有内联统计量，**刻意不转图** |
| Nature Human Behaviour | 3 个 | |
| Frontiers / SAGE / ACM(2) / xlm | 0 个 | 同上，无显示公式 |

> **已修复的真实案例**（用户报的）：第 9 页那条 `v̄ᵢ = (1/N) ∑_{k=k−N+1}^{k} vᵢ(tₖ)`
> 在 PDF 里被拆成 4 个碎片（`vᵢ= 1`、`k∑k=k−N+1`、`vᵢ(tₖ)`、`N`），
> 修复前只有一块被转成图片、另外三块留成文字，上方散文里还残留 `…over Nframes is k ∑ k`。
> 现在 4 块聚成一个区域、整簇出一张图，散文尾部也不再残留公式文本。

> **备选方案（评估后未采用）**：OCR 把公式识别成 LaTeX（pix2tex / Mathpix）再交给 `st.latex` 渲染。
> 需要装 torch（2~3GB）或付费 API，而且**识别错误会"看起来很对"**——对科研阅读来说，
> 一张保真的原图比一个可能算错的公式更安全。

**中文视图下的公式（保持原图，不参与翻译）**

卡片切到「中文」时，正文与章节标题会**按段落分别翻译**，而**公式区域保持原图**不做任何翻译；
「显示全部内容」模式里公式段同样出图、同样不参与翻译，公式文本也不计入卡片词数与翻译字符数。

实现要点：DeepL 与 Google 的接口都支持**一次请求带多段文本**（`text=a&text=b`），
所以「按段落翻译」仍然只发**一次 HTTP 请求**——实测 3 段 1.9 秒 vs 逐段 5.8 秒；
缓存粒度也从「整卡」细化为「段落」，同一段被别的卡片复用时也能命中
（实测来回切换后请求数不再增长，命中数持续增加）。

**安全兜底**：批量调用失败时（例如断网），会退回「整卡翻译」的旧行为并显示错误提示，
所以不会出现「翻译直接坏掉」的新故障模式；公式段与「显示全部内容」下没有段落结构的条目
都会走各自的降级路径，不会把公式文字送进翻译接口。

### 已知限制（阶段 3.5）

| 现象 | 说明 |
| --- | --- |
| 个别卡片会略微超过 300 词上限 | 末尾零头并进上一张时最大到约 390 词，这是为了避免出现很短的尾卡 |
| **公式图不可选中、不可翻译** | 用区域截图换取 100% 视觉保真；中文视图里公式同样保持原图，正文则按段落翻译 |
| **公式判定不是 100%** | 以文字为主的段落刻意不转图片；少数独立公式（页面上没有强候选做种子的）可能仍留作文字。发现漏转或误转，把页码和例子发给我调规则 |
| 同一处公式偶尔被切成两张图 | 例如单栏第 9 页有两处相隔 15pt 的显示公式各出一张图（它们是两处不同的公式，不是切错） |
| 伪代码、公式仍在卡片里 | 它们确实是正文内容，只是排版特殊（以图片形式呈现） |
| 论文标题会出现在第一张卡片开头 | 与顶部元数据区重复，但保持了原文结构 |
| 角色分类不是 100% | 用「显示全部内容」开关 + 人工核对兜底；发现误判可以告诉我调规则；清单行号（单独的 `5`、`6`）有时会被当成页脚，不影响图片本身 |

## 版本管理与回滚

目标：**每次更新都能证明「原有功能没被改坏」，出问题能一键回到上一个可用版本。**

### 一条命令检查有没有改坏

**双击 `回归检查.bat`**（或命令行 `python tests\regression_check.py --suites-dir ..\.dsh-scratch`）。

它会做两件事：

1. **与基线快照逐项比对**：`tests/baseline.json` 里存着 10 篇样本在稳定版本上的全部输出
   （卡片数、词数、角色分布、公式区域数、元数据每个字段的值……），当前结果与之有任何差异都会逐条列出来，
   并且**嵌套字段会展开到子字段**，例如 `元数据.通讯作者：旧值 → 新值`；
2. **跑一遍功能测试套件**：仓库自带的验收套件（随版本进 Git，任何机器上都能跑）**每次都跑**——
   目前是 4.4-A 通讯作者图标标记（17 条断言）；另外用 `--suites-dir ..\.dsh-scratch` 还能带上开发侧的
   临时套件：顺序断言、第九页公式聚类、4.2 作者/单位提取（41 条）、GROBID 客户端（19 条）、交叉校验逻辑（27 条）。

结论只有两种：`原有功能未受影响`（退出码 0）或 `有差异/套件失败`（退出码 1，附逐条差异）。

### 差异出现了怎么办

| 情况 | 处理 |
| --- | --- |
| 差异是**本次故意改的**（例如新增表格截图功能，本来就会改变卡片分段） | 先人工确认每一处差异都符合预期，再刷新基线：`python tests\regression_check.py --update-baseline` |
| 差异**不符合预期** | **不要**刷新基线；回滚（见下）或修代码后重跑 |
| 只是计时/来源说明等易变字段 | 这些放在 `_允许变化` 里，不参与判定，不会误报 |

> 纪律：**刷新基线等于「承认这次变化是对的」**。所以只在逐条确认过差异之后才用 `--update-baseline`，
> 否则这套检查就失去意义了。

### 版本与回滚

```powershell
git tag                                  # 看有哪些版本标记
git log --oneline -12                    # 看最近提交
git checkout v0.4.3                      # 回到某个版本（只读查看）
git switch main                          # 回到主线
git revert <提交号>                       # 撤销某次提交（安全，会生成一条反向提交）
git reset --hard <提交号>                 # 丢弃之后的提交与改动（危险，需谨慎）
```

- 每个稳定版本打一个 tag：`v0.4.1`（4.1 完成）、`v0.4.2`、`v0.4.3`（阶段 4 整体完成）……
- **新功能在分支上开发**（例如 `feat/4.4a-corresponding-icon`），在分支上跑回归检查通过、并经你验收后，
  才合并回 `main` 并打新 tag。这样 `main` 始终是可用的。
- **回滚代码后要同步回滚基线**：先切到目标版本，再在该版本上执行 `--update-baseline` 重新采集，
  否则基线里会留着「未来版本」的输出，导致后续比对全部报差异。

## 协作约定

- 一次只推进一个阶段，通过验收测试并提交后再进入下一阶段。
- 元数据提取遵循「准确性优先于自动化」，任何字段都可人工编辑覆盖。
- 密钥只写在 `.env` 中，`.env` 永不提交。
- 每次改动前先确认基线是干净的（回归检查为 0）；改动后必须重跑一次回归检查，用差异说话。
